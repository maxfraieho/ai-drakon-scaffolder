# Правила підпису іконок та семантичне маркування

Найважливішим етапом у конвеєрі HTSE є семантичне маркування, де LLM-агент трансформує сирий синтаксис Python у "людиночитаємі" підписи, дотримуючись принципу "Clarity is above all". Агент виступає інтелектуальним сортувальником намірів розробника, залишаючи розрахунок геометрії детермінованим рушіям.

### 1. Підпис іконок дій (Action)
Іконка action представляє імперативні команди або обчислення. Основне завдання агента — зменшити візуальний шум (visual clutter) через процес "orphan trimming" (обрізання сиріт), згортаючи тривіальні лінійні операції.
   * Дієслівний підпис vs Код: Залежно від цільової аудиторії діаграми, код result = process_data(items) може залишатися у вигляді коду (для програмістів) або перетворюватися на доменну мову: Обробити дані елементів (для бізнес-аналітиків). За правилами гібридної мови DRAKON-2, збереження чистого коду всередині ікон є стандартною практикою, оскільки цей код пізніше може бути ретрансльований в AST. Проте, складні ланцюжки ініціалізації (x=1; y=2) об'єднуються в один макроблок з роздільником \n.
   * Обробка винятків: Оператор raise ValueError("not found") перетворюється на декларативний підпис дії: Викинути помилку: ValueError.
   * Повернення значень: Оператор return None мапиться як дія return None, після чого її покажчик one обов'язково спрямовується до глобального термінала end алгоритму.
   * Контекстні менеджери (with): Ініціалізація ast.With транслюється у специфічний дієслівний підпис, наприклад, Enter context: open(file). Автоматично впорскується неявний вузол дії Exit context для візуалізації вивільнення ресурсів перед продовженням алгоритму.
   * Ліміти когнітивного навантаження: Максимальна довжина тексту в полі content одного вузла жорстко обмежена 8-10 рядками логіки. Довші фрагменти коду примусово декомпозуються або інкапсулюються у зовнішні підпрограми (макроікона insertion).
   * Мова підпису: Технічні терміни та назви змінних зберігаються оригінальною мовою коду (зазвичай англійською), тоді як структурні пояснення генеруються мовою цільового інтерфейсу користувача.

### 2. Формулювання умов (Question)
Логічні біфуркації (ast.If) формуються виключно у запитальній формі, що забезпечує психологічно комфортне сприйняття вибору між one (Так) і two (Ні).
   * Трансформація коду: Оператор if not name: не залишається сирим синтаксисом. Він конвертується у форму not name? або name порожнє?. Головне правило: текст ікони question завжди закінчується знаком ?.
   * Візуальні логічні формули (Декомпозиція): Класичне програмування допускає складні булеві вирази, такі як if x > threshold and retry < max_retries:. DRAKON розглядає такий запис як антипатерн, оскільки він приховує "short-circuit evaluation" (ранній вихід з умови). Агент зобов'язаний розбивати складні умови (and/or) на каскад окремих ікон question, вибудуваних у формі візуальної "драбинки", що точно відображає порядок обчислення.
   * Умови циклів: Ітерації формалізуються через тексти, що відображають стан ітератора. Для ast.For (for item in items:) текст у макроіконі loop_start записується як for item in items. Для циклів ast.While (while running:) умова перетворюється на запитання running?.

### 3. Іменування гілок Silhouette (Branch / Column Header)
Декомпозиція Силуету вимагає відповідей на "Три питання короля", де заголовок кожної гілки відповідає на питання: "Яка суть цього кроку?".
   * Правило іменування: Гілки (branches) отримують короткі, описові назви етапів бізнес-процесу (наприклад, Ініціалізація БД, Валідація токена). Вони розташовуються зліва направо у строгому хронологічному порядку їх виконання.
   * Guard Clauses та Try/Except: Гілки, що виділяються для ізоляції блоків try/except або обробки дострокових виходів (if not valid: return), автоматично маркуються як обробники помилок. Згідно з евристикою деградації, вони зміщуються вправо і отримують назви, що відображають виняток (наприклад, Обробка ConnectionError).
