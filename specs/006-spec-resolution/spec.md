# Spec 006: Server-resident Harness Spec Resolution (Slice 3.4a)

## Мета

Зафіксувати архітектурний перехід виконання пайплайнів на серверний резолвінг специфікацій безпеки (Harness Specs) для обробника `handleDrakonExecuteDeterministic` у Cloudflare Worker у межах Slice 3.4a. Специфікація закріплює відмову від довіри клієнтським полям `harness_spec`/`gates` у тілі запиту на користь обов'язкової серверної вибірки та валідації конфігурації через `HarnessSpecRepository` (`packages/tenancy`) у базі даних Cloudflare D1, механізм перехідного періоду dual-accept із депрекаційними попередженнями та первинну seed-міграцію дефолтних специфікацій агентів.

## Інваріанти

- [ADR-0020](../../docs/adr/0020-policy-engine-design.md) визначає збереження специфікацій гарнесів у D1 (`harness_specs`), перенесення ролі Policy Enforcement Point (PEP) на Cloudflare Worker та валідацію специфікацій на етапі інгресу.
- [ADR-0025](../../docs/adr/0025-tenancy-boundary.md) встановлює тенантну межу авторизації: виклик `resolveTenant(request)` у Worker є обов'язковим, а доступ до D1 здійснюється виключно через tenant-scoped репозиторії з `tenantId`, зафіксованим у конструкторі.
- Резолвінг специфікацій у `handleDrakonExecuteDeterministic` виконується на стороні сервера через `HarnessSpecRepository` (`packages/tenancy`), що унеможливлює виконання міжтенантних запитів на рівні системи типів.
- Механізм dual-accept: у перехідний період Worker приймає як новий формат запиту (`spec_id`), так і застарілий клієнтський формат (`harness_spec`/`gates`); для застарілого формату генерується deprecation warning та запис в аудит без негайного повернення HTTP 400.
- База даних D1 наповнюється одноразовою seed-міграцією дефолтних специфікацій для чинних конвеєрів `agent_name` (аналог клієнтського `createDefaultSpec(pipelineName)`), що гарантує наявність валідних серверних специфікацій з першого дня впровадження.
- Принцип deny-by-default: запити без знайденої або з невалідною специфікацією відхиляються без передачі виконання до бекенд-функції.

## Межі

Ця специфікація описує архітектурне рішення й інваріанти Slice 3.4a; детальна декомпозиція задач/plan.md ще не існує в цьому репозиторії окремим файлом на момент написання — імплементація виконується паралельним завданням (`agy` на хості `.30`), узгодженим з рішенням ADR-0020. Зміни Slice 3.4b (перенесення human-approval PEP / Adjustment C) знаходяться на етапі аудиту Oracle (Oracle Cloud Claude instance) і повністю винесені за межі цієї специфікації — вони будуть зафіксовані в окремому ADR (ADR-0026 або пізніше). Повне відхилення застарілих клієнтських тіл запитів із помилкою 400 відбудеться в наступному релізі після завершення періоду dual-accept.
