# DRAKON Platform PRD & Planning Document

## SECTION 1 — GRILLING Q5-Q9 (Власні відповіді)

### Q5: Документознавець і архітектор — окремі чи один агент?
**Відповідь**: 
Вони мають бути **окремими спеціалізованими агентами**. 
- **Документознавець (Docs Agent)**: Фокусується виключно на аналізі коду, виявленні бізнес-логіки, структуруванні концептів та веденні файлу `docs/domain.md`. Його контекст налаштований на виділення високорівневої абстракції з деталей реалізації.
- **Архітектор (Architect Agent)**: Фокусується на проектуванні системи на основі `docs/domain.md`, оновленні `solution.json`, генерації модульної структури та створенні файлів-заглушок (`.drakon` схем).
*Обґрунтування*: Поділ обов'язків запобігає перевантаженню контексту (Context Pollution) та дозволяє мати чітко сфокусовані системні промпти, що покращує якість генерації та спрощує відладку роботи кожного окремого агента.

### Q6: drakonwidget — в /codegen, /diagrams, чи нова /project сторінка?
**Відповідь**:
Найбільш ергономічним рішенням є створення єдиної інтегрованої робочої області — **нової сторінки `/workspace` або `/project`** (або розширення сторінки `/diagrams`), яка міститиме:
1. **Ліва панель**: Файлове дерево проекту (документи `docs/`, `.drakon` схеми, згенерований код).
2. **Центральна робоча область**: Вкладка візуального редактора (`drakonwidget`), вкладка перегляду згенерованого коду та вкладка документації.
3. **Права панель**: AI-асистент (чат-панель), який має безпосередній доступ до поточної схеми та дерева проекту.
*Обґрунтування*: Розробнику потрібен цілісний контекст проекту, а не окремі інструменти. `/codegen` має бути точкою входу для створення нових функцій, яка автоматично імпортує результат у робочий простір `/project`.

### Q7: Збірка — сервер (Appwrite Function) чи браузер (drakontechgen client-side)?
**Відповідь**:
**Браузер (drakontechgen client-side)** для швидкого зворотного зв'язку, але з дублюванням у CLI/CI на сервері.
- **Клієнтська частина (drakontechgen.js у браузері)**: Дозволяє компілювати `.drakon` JSON у вихідний код JS/Lua миттєво під час редагування. Це забезпечує нульову затримку (zero-latency execution) та дозволяє локально підсвічувати помилки синтаксису без звернення до API.
- **Серверна частина (Appwrite Function / CLI)**: Необхідна для автоматичної збірки всього проекту при комітах та для роботи автономних агентів, які пишуть код без участі браузера.

### Q8: Auth агентів — Appwrite JWT юзера чи service account?
**Відповідь**:
**Appwrite JWT користувача** для інтерактивних сесій та **Service Account (або довготривалі токени/API Keys)** для повністю фонових/автономних агентів.
- Для дій, які ініціює користувач у браузері, використання його особистого JWT є критичним для правильного логування прав доступу до GitHub та Appwrite.
- Для фонових сервісних завдань (наприклад, автономний рефакторинг або генерація документації вночі) має використовуватися системний сервісний акаунт з обмеженими правами, щоб уникнути помилок через закінчення терміну дії сесії користувача (JWT expiry).

### Q9: MVP scope — що обов'язково зараз, що відкласти?
**Відповідь**:
- **Обов'язково в MVP**:
  1. Інтеграція `drakonwidget` у frontend для візуалізації та ручного редагування `.drakon` JSON.
  2. Браузерна компіляція `.drakon` → JS/Lua за допомогою `drakontechgen.js`.
  3. Пряме збереження/завантаження `.drakon` файлів та відповідного скомпільованого коду в GitHub репозиторій користувача через GitHub API.
  4. Простий чат з агентом у бічній панелі, який може зчитувати відкритий `.drakon` файл та вносити в нього правки.
- **Відкласти (Post-MVP)**:
  1. Підтримка складних типів даних та автодоповнення коду всередині вузлів DRAKON.
  2. Багатокористувацьке редагування в реальному часі.
  3. Візуальний інтерактивний дебаггер (крокування по блок-схемі).
  4. Автоматичне розв'язання конфліктів злиття (merge conflicts) у `.drakon` файлах.

## SECTION 2 — PRODUCT REQUIREMENT DOCUMENT (PRD)

### 1. Problem Statement (Опис проблеми)
Розробка складних алгоритмів традиційним текстовим кодуванням часто призводить до втрати контролю над структурою програми, виникнення логічних помилок у розгалуженнях та складнощів у документуванні. Наявні візуальні редактори (як-от класичний Drakon.Tech) працюють ізольовано від сучасних AI-асистентів, систем контролю версій (GitHub) та командної розробки. Розробникам потрібен інструмент, який поєднує строгість і наочність візуальних схем DRAKON із силою сучасних LLM та зручністю хмарних IDE.

### 2. Solution (Рішення)
**AI-DRAKON Platform** — це інтегроване середовище розробки, де:
1. AI допомагає перетворити текстові вимоги у правильні візуальні алгоритми (блок-схеми DRAKON).
2. Користувач може візуально редагувати ці схеми в реальному часі за допомогою вбудованого `drakonwidget`.
3. Схеми автоматично компілюються в чистий вихідний код прямо у браузері.
4. Весь проект (схеми, код, документація) зберігається безпосередньо у репозиторії GitHub користувача, забезпечуючи повний контроль над даними.

### 3. User Stories (Користувацькі історії x15+)
1. **Авторизація через GitHub**: Як розробник, я хочу авторизуватися в платформі за допомогою свого облікового запису GitHub, щоб мати доступ до своїх репозиторіїв.
2. **Вибір проекту**: Як розробник, я хочу вибрати активний GitHub репозиторій зі списку, щоб завантажити його структуру у робочий простір.
3. **Стартове інтерв'ю з Документознавцем**: Як користувач, я хочу пройти текстове інтерв'ю з AI-агентом для опису нової системи, щоб зафіксувати загальні вимоги.
4. **Автоматична генерація Domain MD**: Як розробник, я хочу, щоб Docs-Agent автоматично створив або оновив файл `docs/domain.md` на основі нашого інтерв'ю.
5. **Генерація структури проекту Архітектором**: Як розробник, я хочу, щоб Architect-Agent проаналізував `docs/domain.md` та створив файл конфігурації `solution.json` з описом модулів та функцій.
6. **Створення скелетних схем**: Як розробник, я хочу, щоб Архітектор автоматично завантажив у мій репозиторій `.drakon` файли-заглушки для всіх запланованих функцій.
7. **Візуалізація схеми**: Як розробник, я хочу бачити обрану функцію у вигляді інтерактивної схеми DRAKON у робочій області.
8. **AI-генерація тіла функції**: Як користувач, я хочу ввести текстовий опис логіки функції (наприклад, "сортування масиву бульбашкою"), щоб AI згенерував відповідні вузли блок-схеми.
9. **Візуальне редагування схеми**: Як розробник, я хочу додавати, видаляти та переміщувати вузли дії (action) та умови (question) на схемі за допомогою миші.
10. **Редагування вмісту вузлів**: Як розробник, я хочу мати можливість писати код або текстові інструкції всередині вузлів блок-схеми.
11. **Миттєва компіляція**: Як розробник, я хочу бачити згенерований код (JavaScript або Lua) у сусідній вкладці одразу після збереження змін на схемі.
12. **Комміт змін у GitHub**: Як розробник, я хочу натиснути кнопку "Зберегти в GitHub", щоб автоматично створити комміт із новими версіями `.drakon` JSON та скомпілованого коду.
13. **Валідація правил DRAKON**: Як розробник, я хочу отримувати візуальні попередження, якщо моя схема порушує правила DRAKON (наприклад, перетин ліній розгалуження чи відсутність виходу).
14. **Чат з контекстом схеми**: Як користувач, я хочу поставити запитання AI-агенту про поточну схему (наприклад, "де тут можливе зациклення?"), щоб отримати контекстну відповідь.
15. **Експорт проекту**: Як розробник, я хочу скомпілювати весь проект в один вихідний файл відповідно до зв'язків у `solution.json`.
16. **Зворотне трасування помилок**: Як розробник, я хочу клікнути на рядок скомпільованого коду з помилкою, щоб автоматично сфокусувати відповідний вузол на схемі DRAKON.

### 4. Implementation Decisions (Технічні рішення)
- **Файлова структура в репозиторії**:
  - `solution.json` — метадані проекту, список модулів та їхні взаємозв'язки.
  - `docs/domain.md` — опис доменної моделі та специфікації функцій.
  - `src/modules/<module_name>/<function_name>.drakon` — JSON-серіалізована схема кожної окремої функції.
  - `src/generated/output.js` (або `.lua`) — результат фінальної збірки проекту.
- **Frontend двигун**: Використання `stepan-mitkin/drakonwidget`, адаптованого для роботи в React-компонентах. Взаємодія здійснюється через імпорт/експорт стандартного об'єкта `.drakon`.
- **Компілятор**: Клієнтська бібліотека `drakontechgen.js` завантажується динамічно та виконує генерацію коду безпосередньо у браузері.

### 5. Testing Decisions (Стратегія тестування)
- **Unit-тести**: Тестування транслятора `.drakon` JSON → Код за допомогою набору еталонних схем (тести на правильність розгалужень, циклів та обробки винятків).
- **Integration-тести**: Перевірка взаємодії між Appwrite Function (`drakon-codegen`) та Cloudflare Worker, зокрема логування результатів генерації та відстеження статусів виконання.
- **E2E-тести**: Симуляція повного циклу розробки користувачем: створення проекту → генерація схеми AI → ручне редагування → комміт в тестовий репозиторій GitHub.

### 6. Out of Scope (Поза межами проекту)
- Власний хостинг Git-репозиторіїв (використовується виключно GitHub).
- Підтримка мов програмування, відмінних від JavaScript, Lua та Clojure на етапі MVP.
- Локальне виконання та дебаг згенерованого коду (виконання відбувається у середовищі користувача).

### 7. Further Notes (Додаткові примітки)
- Необхідно враховувати обмеження швидкості запитів (Rate Limits) до GitHub API при інтенсивному збереженні схем.
- Збереження проміжних станів редагування у `localStorage` для запобігання втраті даних користувача при розриві з'єднання.

## SECTION 3 — ISSUES (Мінімум 10)

1. **Category**: `Authentication`
   - **Summary**: Відсутність автоматичного оновлення Appwrite JWT при тривалій роботі з IDE.
   - **Current**: Сесія користувача переривається через 15 хвилин, ламаючи запити до API.
   - **Desired**: Додати фоновий механізм періодичного оновлення токенів (Silent Token Refresh) кожні 10 хвилин.
   - **Interfaces**: `src/lib/appwrite.ts`, `src/lib/codegen/codegenApi.ts`
   - **Criteria**: IDE працює безперервно протягом годин без потреби повторного входу користувача.
   - **OutOfScope**: Підтримка сесій на базі cookies для сторонніх доменів.
   - **Complexity**: `Low`

2. **Category**: `Editor`
   - **Summary**: Інтеграція `drakonwidget` в React життєвий цикл.
   - **Current**: Немає візуального відображення схем, лише текстовий/JSON вигляд.
   - **Desired**: Створити обгортку React-компонента для `drakonwidget`, що ініціалізує полотно та реагує на зміну пропсів.
   - **Interfaces**: `src/components/drakon/DrakonEditor.tsx`, `public/drakonwidget/`
   - **Criteria**: Схема успішно рендериться на сторінці, підтримує zoom та drag-n-drop елементів.
   - **OutOfScope**: Кастомізація стилів вузлів за межами стандартної палітри DRAKON.
   - **Complexity**: `High`

3. **Category**: `Codegen`
   - **Summary**: Валідація згенерованого LLM `.drakon` JSON.
   - **Current**: LLM може повернути синтаксично неправильний JSON або схему з порушенням логічних зв'язків.
   - **Desired**: Додати валідатор схеми на стороні Appwrite функції перед відправкою клієнту.
   - **Interfaces**: `services/drakon-codegen/src/main.ts`
   - **Criteria**: У разі помилки валідації AI робить авто-спробу виправити промпт або повертає зрозумілу помилку.
   - **OutOfScope**: Автоматичне виправлення семантичних помилок у коді користувача.
   - **Complexity**: `Medium`

4. **Category**: `Build`
   - **Summary**: Підтримка клієнтської компіляції через `drakontechgen`.
   - **Current**: Файли `.drakon` завантажуються, але код з них генерується лише на серверній стороні.
   - **Desired**: Браузерний імпорт `drakontechgen.js` та локальний виклик `buildGenerator` для миттєвого отримання коду.
   - **Interfaces**: `src/pages/CodegenPage.tsx`, `public/drakontechgen.js`
   - **Criteria**: Зміна блок-схеми оновлює вкладку з кодом менш ніж за 100мс.
   - **OutOfScope**: Оптимізація та мініфікація згенерованого коду.
   - **Complexity**: `Medium`

5. **Category**: `Git`
   - **Summary**: Прямий комміт змін у GitHub репозиторій з браузера.
   - **Current**: Користувач змушений копіювати код вручну або запускати локальні скрипти.
   - **Desired**: Кнопка збереження відправляє комміт безпосередньо у вибрану гілку репозиторію через API.
   - **Interfaces**: `src/lib/api.ts`, `src/pages/WorkspacePage.tsx`
   - **Criteria**: У репозиторії з'являється новий комміт з оновленими `.drakon` та `.js` файлами.
   - **OutOfScope**: Керування кількома гілками (branches) та створення Pull Requests з інтерфейсу.
   - **Complexity**: `Medium`

6. **Category**: `Agent`
   - **Summary**: Інтеграція Архітектора з `solution.json`.
   - **Current**: Агент створює файли хаотично, без єдиного реєстру модулів.
   - **Desired**: Architect Agent при створенні нових функцій обов'язково реєструє їх у файлі `solution.json`.
   - **Interfaces**: `services/architect-agent/ai_chat/architect_chat.py`
   - **Criteria**: Файл `solution.json` завжди містить актуальний список наявних у проекті модулів та функцій.
   - **OutOfScope**: Автоматичне видалення старих модулів без підтвердження користувача.
   - **Complexity**: `Medium`

7. **Category**: `Workspace`
   - **Summary**: Файлове дерево проекту.
   - **Current**: Відсутня візуальна структура проекту, складно перемикатися між файлами.
   - **Desired**: Інтегрувати бічну панель з деревом файлів репозиторію з можливістю відкривати `.drakon` та `.md` файли.
   - **Interfaces**: `src/components/workspace/FileTree.tsx`
   - **Criteria**: Клік на файл у дереві відкриває відповідний редактор у робочій області.
   - **OutOfScope**: Контекстне меню файлів (створення/видалення папок мишкою — це робиться через команди або AI).
   - **Complexity**: `Medium`

8. **Category**: `Codegen`
   - **Summary**: Генерація умовних переходів (Question Nodes) за допомогою AI.
   - **Current**: AI генерує переважно лінійні послідовності кроків.
   - **Desired**: Промпт для LLM розширено прикладами розгалужень (IF-ELSE) для створення складніших алгоритмів.
   - **Interfaces**: `services/drakon-codegen/src/main.ts`
   - **Criteria**: AI успішно створює вузли типу `question` з правильними переходами `one` (Yes) та `two` (No).
   - **OutOfScope**: Генерація вкладених циклів глибиною понад 3 рівні.
   - **Complexity**: `High`

9. **Category**: `Build`
   - **Summary**: Збірка багатомодульного проекту.
   - **Current**: Схеми компілюються окремо, взаємозв'язки між файлами не враховуються.
   - **Desired**: Розробити пакувальник (linker), який обходить `solution.json` та збирає всі скомпільовані модулі в один файл.
   - **Interfaces**: `src/lib/codegen/linker.ts`
   - **Criteria**: Фінальний файл містить усі функції з правильним імпортом/експортом та готовий до запуску.
   - **OutOfScope**: Створення sourcemaps для скомпільованого файлу.
   - **Complexity**: `High`

10. **Category**: `UI/UX`
    - **Summary**: Візуальна підсвітка синтаксичних помилок на схемі.
    - **Current**: Помилки компіляції показуються загальним списком у консолі або тості.
    - **Desired**: Конкретний вузол DRAKON, у якому сталася помилка компіляції, підсвічується червоним кольором на схемі.
    - **Interfaces**: `src/components/drakon/DrakonEditor.tsx`, `public/drakonwidget/`
    - **Criteria**: При отриманні помилки від `drakontechgen` відповідний вузол з id помилки змінює стиль рамки.
    - **OutOfScope**: Автоматичне виправлення синтаксису в текстовому полі вузла.
