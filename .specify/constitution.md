## 2. Фундаментальні інваріанти розробки та безпеки

### 🔒 Інваріант — Політика PII та конфіденційності
- Жодні персональні дані, секрети чи облікові дані **НЕ МОЖУТЬ бути закомічені у Git-репозиторій**.
- Усі конфіденційні файли зберігаються виключно в `~/.ai-drakon-scaffolder-secrets`.
- LLM-арбітр (якщо увімкнений) НЕ надсилає diff по шляхах: `*.txt,credentials.json,*.db,*.secret`.

### 📐 Критерій ADR-значущості
Архітектурні рішення документуються окремо від `spec.md` у форматі MADR
v3.x (`docs/adr/NNNN-slug.md`, наскрізна нумерація, шаблон
`docs/adr/template.md`). ADR — джерело кандидатів для майбутніх
інваріантів цього розділу, сам по собі НЕ новий шар пріоритету:
конституція лишається найвищим шаром.

Рішення потребує ADR, якщо відповідає ХОЧА Б ОДНОМУ з критеріїв:
1. Впливає на нефункціональні характеристики (безпека, продуктивність,
   стабільність з'єднання чи детермінізм).
2. Дорого відкотити (вибір СУБД/мови/протоколу/структури даних).
3. Існує 2+ життєздатних альтернативи з реальними trade-off'ами.
4. Змінює межі/контракт між підсистемами.
5. Встановлює новий системний інваріант для розробників/агентів.

Локальна деталь реалізації фічі — лишається в `spec.md`, ADR не
обов'язковий. Перевірка чекліста виконується на Plan-кроці ПЕРЕД
переходом у `tasks.md`.

## 3. Правила SDD Workflow (`specify-cli`)

> Три шари, не плутати: **конституція** (цей файл) = інваріанти.
> **Методологія** (`docs/for-agents/sdd-development-methodology.md`) = процедура.
> **Native-команди / project-команди / скіли** = лише транспорт виклику.
> За конфліктом між шарами виграє конституція.

| Фаза SDD | Native primitive (Spec Kit Agent Skill) | Project command | Спільний скіл |
|---|---|---|---|
| Specify | `speckit-specify` | `/sdd:feature` | `.agents/skills/sdd-feature` |
| Clarify | `speckit-clarify` | `/sdd:clarify` | `.agents/skills/speckit-clarify` |
| Plan | `speckit-plan` | (у складі шаблонів) | `.agents/skills/speckit-plan` |
| Tasks | `speckit-tasks` | (у складі шаблонів) | `.agents/skills/speckit-tasks` |
| Implement | `speckit-implement` | `/sdd:{bugfix,refactor,integration,teaching}` | `.agents/skills/sdd-*` |
| Verify | — | `/sdd:verify` | `bin/sdd_verify.sh` |

Native Spec Kit механізм — це **Agent Skills** (frontmatter `name`+`description`, семантична активація), НЕ буквальні slash-команди. Встановлюється по одному: `specify integration install <key>` для кожного з `claude,codex,agy` (окремою командою на кожен ключ — `install` не приймає список).

Усі нові фічі, рефакторинг або зміни API описуються за специфікаційним циклом:

1. `/sdd:feature` (project) або семантична активація `speckit-specify` (native): специфікація у `specs/<feature-name>/spec.md`.
2. Розробка архітектурного плану з аналізом впливу через gitnexus.
2.1. Перед переходом у Tasks: звір рішення проти чекліста ADR-значущості (§2). Якщо відповідає хоч одному пункту — створи `docs/adr/NNNN-slug.md` ПЕРЕД `tasks.md`; план посилається на нього замість дублювання обґрунтування.
3. Декомпозиція на атомарні задачі з критеріями приймання (AC).
4. Послідовне виконання, перевірка після кожного кроку.
5. `bash bin/sdd_verify.sh --gate` перед комітом.
