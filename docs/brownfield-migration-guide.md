# Brownfield Migration Guide — впровадження SDD на існуючий проєкт

> На відміну від greenfield (`copier copy` в порожню директорію), тут код
> вже написаний, роками накопичував неявні рішення, і найгірше що можна
> зробити — почати переписувати "надлишковий" код без розуміння навіщо він
> існує. Ця директорія — 4-фазний roadmap, кожна фаза — окрема, з власними
> gate'ами перед переходом далі. Не "big bang".

## Фаза 1 — Контекст і read-only операції

Мета: агент розуміє реальний стан коду ДО того, як почне його редагувати.

- **Context Engineering:** заповни `AGENTS.md` конкретними, а не маркетинговими фактами — команди білда, тестові раннери, семантика директорій, відомі обмеження ("не чіпай `/legacy/billing`, там нема тестів").
- **Doubt-Driven Development:** твердження агента про існуючий код МУСЯТЬ вважатись потенційно хибними, доки не підтверджені інспекцією коду. Перед будь-якою правкою — цитата `файл:рядок`, не переказ з пам'яті.
- Використовуй gitnexus для картографування залежностей ДО першої правки — не грепай навмання.

**Deliverable фази:** `specs/000-baseline/spec.md` — реверс-інжинірингом відновлена специфікація поточної поведінки (не бажаної, а фактичної).

## Фаза 2 — Захист наявних поверхонь коду

Мета: не зламати те, що вже працює, поки не почав це чіпати.

- **Characterization Testing:** для будь-якого legacy-коду, що плануєш змінювати, спершу напиши тест, що фіксує ФАКТИЧНУ поведінку (не бажану). "Beyoncé Rule": якщо на поведінку хтось покладається — вона МУСИТЬ бути замкнена тестом до будь-яких змін.
- **Chesterton's Fence:** заборонено видаляти чи спрощувати "надлишкові" структури (вкладені retry-цикли, здавалось б мертвий код) без документованого пояснення, навіщо вони існують. Приклад цього патерна вже в `bin/sdd_verify.sh` — WARN замість FAIL для legacy spec-директорій без `spec.md`, а не ретроактивне ламання історії.

## Фаза 3 — Two-speed multi-agent adoption

Мета: нові фічі йдуть повним SDD-циклом, legacy — лише під захистом Фази 2.

- **Legacy код:** правиться лише через `/sdd:bugfix`/`/sdd:refactor` під сіткою characterization-тестів.
- **Нові фічі:** повний цикл `/sdd:feature` → план → tasks → implement.
- **Контракти на межах:** де нове стикається зі старим — явний контракт (OpenAPI, схема, типізований інтерфейс), не неявна довіра.
- **Мультиагентний handoff:** `.specify/feature.json` координує хто (`owner_agent`) на якій фазі — навіть якщо legacy-роботу робить один агент, а нову фічу інший.
- **Арбітр лишається `shadow`**, доки не набереться baseline точності на реальних verdict'ах — вмикати `blocking` до цього моменту передчасно.

## Фаза 4 — Активне погашення технічного боргу

- Дисциплінована deprecation-політика (спершу advisory-попередження, потім видалення).
- Observability на legacy-інтерфейсах (структуровані логи, RED-метрики) — оптимізуй на основі реальної телеметрії, не здогадок.
- `- [ ]` незакриті задачі рахуються `bin/sdd_verify.sh --gate` — борг видно, не ховається.
- Арбітр промотується в `blocking`, `copier update` підтягує оновлення шаблону.

## Реверс-інжиніринг specs з коду без оригінальної специфікації

Коли натрапляєш на компонент без жодної документації:

1. Картографуй публічні інтерфейси через gitnexus — реальні роути, моделі, активна поведінка.
2. Компілюй у проміжну схему (OpenAPI/JSON Schema) — валідовану, не прозову.
3. На основі схеми + історії комітів/міграцій БД склади ретроактивний `spec.md`: user stories реконструйовані з активних ендпоінтів, функціональні обмеження, явні межі.
4. Людський рев'ю ретроактивного spec.md ОБОВ'ЯЗКОВИЙ — це реконструкція, не факт.

## Пріоритезація: з чого почати

Не роби "big bang" на весь кодову базу. Почни з систем з високою частотою змін і документованими проблемами продуктивності — там найбільший ROI. Стабільні, рідко змінювані компоненти — залиш насамкінець або взагалі поза скоупом Фази 3.
