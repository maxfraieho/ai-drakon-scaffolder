# Посібник ручного тестування UI — UAV-Watcher

Цей документ містить детальний план ручного тестування користувацького інтерфейсу платформи **AI-DRAKON** у контексті інтеграції з проектом моніторингу повітряних загроз **UAV-Watcher**. 

---

## 1. Передумови

Перед початком тестування необхідно переконатися, що виконано наступні вимоги:

1. **Обліковий запис для авторизації:**
   - Логін: `owner`
   - Пароль: `drakon-mcp-2026`
2. **Адреса веб-інтерфейсу:** [AI-DRAKON UI](https://ai-drakon-scaffolder.pages.dev)
3. **Налаштований репозиторій GitHub:** `maxfraieho/uav-watcher`
4. **Корисні посилання:**
   - Посібник з Pipeline A: [[manuals/manual-pipeline-a]]
   - Загальна архітектура системи: [[architecture/_INDEX]]

## 2. Тест-кейси для сценаріїв тестування (A–G)

### TC-A-01: Сценарій A — Код → DRAKON IR
* **Функція uav-watcher:** `score_proximity` (рядки 78-105 у `uav_watcher.py`) — обчислення наближеності загрози до міста.
* **Кроки:**
  1. Авторизуватися в інтерфейсі під обліковим записом `owner / drakon-mcp-2026`.
  2. Перейти в розділ **Код** (роут `/code`).
  3. У файловому браузері відкрити файл `uav_watcher.py` та знайти функцію `score_proximity` (рядки 78-105).
  4. Натиснути кнопку **Аналізувати** для ініціалізації Pipeline A.
* **Очікуваний результат:** На екрані з'являється індикатор завантаження `Loading...`. Протягом 10-30 секунд відбувається генерація DRAKON IR. Користувача перенаправляє у розділ **Схеми** (`/diagrams`), де з'являється нова згенерована діаграма для `score_proximity` з візуальними блоками умов і циклів.
* **Посилання:** [[manuals/manual-pipeline-a]]

### TC-B-01: Сценарій B — Ідея → IR
* **Функція uav-watcher:** "AllerClear sync flow — автосинхронізація відбою" (`send_allclear_notification` та `_catchup_history`).
* **Кроки:**
  1. Перейти в розділ **Конвеєри** (роут `/pipelines`) та обрати **Сценарій B (Ідея → IR)**.
  2. У полі введення текстового опису ідеї вставити:
     `"AllerClear sync flow: catch up recent history to verify if threat active has resolved and send allclear notification"`
  3. Натиснути кнопку **Згенерувати IR**.
* **Очікуваний результат:** AI-агент розробляє логіку автосинхронізації відбою і генерує коректний DRAKON IR JSON-граф, який можна відкрити та переглянути у вигляді схеми ДРАКОН.
* **Посилання:** [[manuals/manual-pipeline-b]]

### TC-C-01: Сценарій C — Тест-кейси
* **Функція uav-watcher:** `keyword_classify` — швидкий класифікатор за ключовими словами без AI.
* **Кроки:**
  1. Перейти на сторінку `/pipelines` та обрати **Сценарій C (Тест-кейси)**.
  2. Завантажити функцію `keyword_classify` з коду `uav_watcher.py`.
  3. Натиснути кнопку **Згенерувати тест-кейси**.
* **Очікуваний результат:** Система генерує набір тест-кейсів для Python, які покривають наступні гілки:
  - Наявність ключового слова відбою (`_ALLCLEAR_PATTERNS` -> `False`)
  - Збіг ключового слова міста та паттерну загрози (`_THREAT_PATTERNS` -> `True`)
  - Оголошення тривоги у місті (`_AIRARAID_PATTERNS` -> `True`)
  - Невизначений випадок, що потребує перевірки AI (`None`)
* **Посилання:** [[kb/_INDEX]]

### TC-D-01: Сценарій D — Рефакторинг
* **Функція uav-watcher:** `score_proximity` — оптимізація цикломатичної складності (CC ≈ 5, 4 послідовні цикли `for`).
* **Кроки:**
  1. Перейти на сторінку `/pipelines` та обрати **Сценарій D (Рефакторинг)**.
  2. Вставити код функції `score_proximity` із 4 послідовними циклами пошуку ключових слів.
  3. Натиснути кнопку **Запропонувати рефакторинг**.
* **Очікуваний результат:** AI-агент пропонує оптимізовану версію функції (наприклад, з об'єднаним проходом по паттернах або використанням регулярного виразу), що зменшує цикломатичну складність та вкладеність циклів, зберігаючи при цьому початкову логіку нарахування балів близькості загрози.
* **Посилання:** [[kb/_INDEX]]

### TC-E-01: Сценарій E — Пояснення
* **Функція uav-watcher:** `threat_detection` flow (асинхронний обробник `handler` для нових повідомлень Telegram у `uav_watcher.py`, рядки 487-639).
* **Кроки:**
  1. Перейти на сторінку `/pipelines` та обрати **Сценарій E (Пояснення)**.
  2. Завантажити блок коду функції `handler` з `uav_watcher.py`.
  3. Натиснути кнопку **Пояснити код**.
* **Очікуваний результат:** Агент надає чітке та структуроване пояснення роботи конвеєра виявлення загроз:
  - Фільтрація повідомлень за регіональним паттерном (`region_pattern_search`).
  - Виклик пайплайну класифікатора LangGraph або резервного `ai_classify`.
  - Запобігання спаму (Flood control / Throttle) через `_channel_throttles`.
  - Надсилання прямих пуш-сповіщень членам сім'ї у разі високої загрози (HIGH/CRITICAL) з бази `families.db`.
  - Логування подій у БД через `save_threat_event` та публікація сповіщень.
* **Посилання:** [[kb/_INDEX]]

### TC-F-01: Сценарій F — Специфікація
* **Функція uav-watcher:** "Sharon Consultant — query → LangGraph → shelters" — інтеграція чат-бота Sharon з пошуком найближчих укриттів.
* **Кроки:**
  1. Перейти на сторінку `/pipelines` та обрати **Сценарій F (Специфікація)**.
  2. Задати тему специфікації: `"Sharon Consultant: RAG-пошук укриттів через Overpass API та інтеграція з LangGraph"`.
  3. Натиснути кнопку **Згенерувати специфікацію**.
* **Очікуваний результат:** Агент генерує технічну специфікацію для інтеграції, яка описує взаємодію між запитом користувача, LangGraph-агентом, кешем укриттів `shelters_cache.json` та викликом Overpass API.
* **Посилання:** [[kb/_INDEX]]

### TC-G-01: Сценарій G — Пакетний аналіз (Batch)
* **Функція uav-watcher:** весь модуль `uav_watcher.py` (загальний аналіз).
* **Кроки:**
  1. Перейти на сторінку `/pipelines` та обрати **Сценарій G (Пакетний аналіз)**.
  2. Обрати репозиторій `maxfraieho/uav-watcher` та запустити аналіз для всього файлу `uav_watcher.py`.
  3. Натиснути кнопку **Запустити Batch аналіз**.
* **Очікуваний результат:** Повний звіт про архітектурну структуру файлу `uav_watcher.py` із виявленням всіх точок інтеграції (Telethon, Telegram Bot API, SQLite `families.db`, Sharon LangGraph pipeline) та рекомендаціями щодо покращення.
* **Посилання:** [[kb/_INDEX]]

## 3. Тестування секцій UI

Під час проведення ручного тестування необхідно детально перевірити функціональність та інтерфейс наступних розділів платформи:

### 1. Браузер коду (`/code`)
* **Опис:** Інтерфейс інтегрованого браузера файлів репозиторію GitHub.
* **Елементи тесту:**
  - Перевірка відображення дерева файлів для репозиторію `maxfraieho/uav-watcher`.
  - Відкриття файлу `uav_watcher.py` у вбудованому редакторі коду Monaco.
  - Робота кнопки **Аналізувати** для виділених функцій.
  - Наявність індикаторів завантаження під час виконання аналізу.

### 2. Сценарії конвеєрів (`/pipelines`)
* **Опис:** Інтерактивна панель керування 7 сценаріями (A–G).
* **Елементи тесту:**
  - Перемикання між усіма 7 вкладками сценаріїв.
  - Валідація форм введення (код, текстові описи ідей, параметри специфікації).
  - Відображення результатів генерації (код, JSON IR, специфікації).

### 3. Редактор схем (`/diagrams`)
* **Опис:** Інтерфейс відображення та ручного редагування схем ДРАКОН.
* **Елементи тесту:**
  - Відображення списку згенерованих схем.
  - Коректність відображення назв схем (відсутність пошкоджених Юнікод-символів).
  - Перевірка відкриття та візуалізації схеми (блоки Початок, Кінець, Умови, Дії, стрілки переходів).
  - Можливість ручного перетягування та редагування вузлів схеми.

### 4. Агенти (`/agents`)
* **Опис:** Інспекція та взаємодія з AI-агентами платформи.
* **Елементи тесту:**
  - Перевірка наявності 3 основних агентів: **DRAKON Agent**, **ARCHITECT Agent**, **DOCS Agent**.
  - Робота панелі інспектора: перевірка налаштованої моделі (наприклад, `drakon-assistant-proxy`).
  - Чат з агентом у нижній частині інтерфейсу: можливість відправки запитів та отримання відповідей.

### 5. Нотатки (`/notes`)
* **Опис:** Секція для збереження архітектурних та тестових нотаток.
* **Елементи тесту:**
  - Відображення списку нотаток.
  - Перевірка функціональності створення, редагування та видалення нотаток.
  - Оцінка наявності інформативних заглушок, якщо список нотаток порожній.

## 4. Критерії Pass/Fail

Тест-кейс вважається **пройденим (Pass)**, якщо:
1. Всі кроки виконуються без виникнення критичних помилок (наприклад, HTTP 500, зависання інтерфейсу, ERR_CONNECTION_REFUSED на життєво важливих роутах).
2. Очікуваний результат повністю відповідає описаному в тест-кейсі.
3. Елементи інтерфейсу (модальні вікна, списки діаграм) оновлюються коректно після завершення асинхронних операцій.

Тест-кейс вважається **проваленим (Fail)**, якщо:
1. Інтерфейс блокується або аварійно завершує роботу (білий екран, нескінченний loading state).
2. Запити до MCP-сервера повертають помилки авторизації або з'єднання, які не обробляються UI належним чином.
3. Згенерована діаграма не відповідає стандартам представлення мови ДРАКОН (наприклад, відсутні зв'язки між блоками).

## 5. Відомі обмеження та проблеми

При проведені тестування необхідно враховувати наступні відомі проблеми та обмеження, зафіксовані в карті проблем проекту:
* **Блокуючі проблеми:**
  - Якщо GitHub Personal Access Token не налаштований у налаштуваннях (`Settings`), ліва панель `/code` показуватиме помилку **"Не вдалося завантажити"**.
  - Інтеграція OpenDesign наразі недоступна (`ERR_CONNECTION_REFUSED` за адресою `http://192.168.3.234:7459`), оскільки сервіс не запущений на Raspberry Pi.
* **Проблеми високого пріоритету (High):**
  - **Відсутній фідбек після натискання "Аналізувати"** в `/code` — операція запускається у фоні, але UI не відображає прогрес аналізу належним чином (немає спінера або тоста).
  - **Немає авто-оновлення у `/diagrams`** — після завершення аналізу нова діаграма генерується в БД, але список схем не оновлюється без перезавантаження або переходу вручну.
  - **"Агент тимчасово недоступний"** для `Architect Agent` без деталей помилки, якщо токен проксі порожній (`PROXY_TOKEN=""`).
  - Попередження **"Модель невідома"** у вкладці `/agents` для проксі-агента, якщо не налаштована конкретна LLM-модель.
* **Проблеми середнього пріоритету (Medium):**
  - Некоректне кодування (Юнікод сміття) у деяких назвах схем у списку `/diagrams` (наприклад, `SlotRouter â㎝ score_candidate...`).
  - Розділ `/notes` є пустим та неінтерактивним (немає стартового шаблону або кнопки створення першої нотатки).

* **Посилання на детальну карту проблем:** [[../uav-watcher-analysis/problem-map]]
