## Знайдені проблеми
1. **Помилка 404 у розділі Pipeline:** Сторінка `/pipeline` повністю недоступна, що унеможливлює візуальну побудову та моніторинг ланцюжків виконання.
2. **Проблема кодування (Mojibake) у списку схем:** Назва файлу відображається з артефактами (`â` замість коректного юнікод-символу), що вказує на некоректне декодування файлових імен на бекенді або при передачі через API.
3. **Нав'язливе вікно "Save password?" в Chrome:** Спливаюче вікно браузера блокує центр екрану на кількох сторінках. Це зазвичай викликано використанням полів вводу з типами або атрибутами, які помилково інтерпретуються менеджером паролів як логін/пароль (наприклад, поле пошуку або текстовий input без автозаповнення `autocomplete="new-password"` чи `autocomplete="off"`).
4. **Запит на доступ до локальної мережі:** Запит "Access other devices on your local network" виникає, оскільки веб-додаток (запущений на публічному хостингу Pages) намагається робити прямі HTTP-запити на локальні IP-адреси (наприклад, MinIO, n8n чи локальний API розробника), що блокується політикою безпеки CORS/Mixed Content.
5. **Невідома модель у DRAKON AI Assistant:** Асистент пише "модель невідома" для `drakon-assistant-proxy`, що вказує на відсутність зв'язку з проксі або некоректні налаштування моделі в конфігурації.
6. **Відсутність токена GitHub:** Без налаштованого PAT неможливо синхронізувати та зберігати зміни схем безпосередньо у репозиторій.

## Рекомендовані DRAKON схеми для uav-watcher

### 1. Threat Detection Pipeline
Схема для візуалізації процесу класифікації загрози з Telegram-повідомлення:
- **Початок:** Message received from Telethon monitoring.
- **Крок 1 (GeoFilter):** Перевірка тексту повідомлення на гео-ключі (Settlements в радіусі 30км від активних локацій з `families.db` + міста з конфігу).
- **Умова (Matched?):** Якщо ні -> завершити (Ignore). Якщо так -> переходимо до кроку 2.
- **Крок 2 (Proximity Scorer):** Розрахунок Proximity Score (1-10) на основі ключових слів.
- **Крок 3 (LangGraph Threat Classifier):**
  - `extract_entities` за допомогою LLM (Gemini 2.5 Flash).
  - `assess_severity` для визначення рівня загрози (LOW, MEDIUM, HIGH, CRITICAL).
- **Умова (Severity >= MEDIUM?):** Якщо ні -> завершити. Якщо так -> `format_message` та перехід до кроку 4.
- **Крок 4 (Alert Dispatcher):**
  - Перевірка лімітів (Flood Control 180s, Cooldown 90s).
  - Якщо пройдено -> надсилання в Telegram-канал сповіщень.
  - Якщо загроза HIGH або CRITICAL -> direct push сповіщення членам сімей.
- **Кінець.**

### 2. AllClear Sync
Схема для автоматичного відстеження та відправки відбою повітряної тривоги (All Clear):
- **Початок:** Отримання повідомлення про відбій або спрацювання таймера таймауту загрози.
- **Крок 1:** Перевірка, чи є активні загрози в базі (`_active_threat == True`).
- **Умова (Active threat exists?):** Якщо ні -> завершити. Якщо так -> переходимо до кроку 2.
- **Крок 2:** Скидання глобальних статусів (`_active_threat = False`, обнулення рівнів загрози).
- **Крок 3:** Генерація тексту повідомлення про відбій ("Увага! Відбій повітряної тривоги").
- **Крок 4:** Відправка повідомлення у Telegram-канал та direct push користувачам.
- **Кінець.**

### 3. Sharon Consultant Flow
Схема діалогового асистента для обробки запитів користувачів:
- **Початок:** User message received via `/chat` endpoint (FastAPI).
- **Крок 1:** Нормалізація запиту та аналіз психологічного стану користувача (Active Threat, Panic, Stupor, Dissociation, Suicidal risk, Normal).
- **Умова (Crisis state?):**
  - **Так (Паніка/Суїцидальний ризик):** Застосувати строгий директивний протокол без markdown розмітки (короткі фрази, інструкції дії). Перехід до кроку 4.
  - **Ні:** Перехід до кроку 2.
- **Крок 2 (RAG Retrieval):** Пошук відповідної інформації в локальній базі знань (Markdown Guides) та завантаження останніх подій загроз з `families.db` для контексту.
- **Умова (Found in KB?):**
  - **Ні:** Виконати веб-пошук через DuckDuckGo Search API.
  - **Так:** Використати знайдені матеріали.
- **Крок 3:** Формування фінальної відповіді за допомогою LLM-проксі (Gemini).
- **Крок 4:** Відправка відповіді користувачеві.
- **Кінець.**

### 4. Shelter Search
Схема для пошуку найближчих укриттів при отриманні гео-запиту:
- **Початок:** Користувач запитує укриття або надсилає геолокацію.
- **Крок 1:** Визначення координат GPS користувача (з бази `families.db` або параметрів запиту).
- **Крок 2:** Запит до Overpass API / OpenStreetMap для пошуку укриттів (shelters) у радіусі 1–5 км від координат.
- **Умова (Shelters found?):**
  - **Ні:** Повідомити про відсутність укриттів поруч, надати загальні правила безпеки (правило двох стін).
  - **Так:** Переходимо до кроку 3.
- **Крок 3:** Сортування знайдених укриттів за відстанню (найближчі першими), фільтрація за доступністю.
- **Крок 4:** Формування списку з назвами, адресами та посиланнями на мапу. Відправка результатів.
- **Кінець.**
