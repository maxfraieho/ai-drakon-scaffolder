# Genspark-on-Astryx Redesign — план

Гілка: `feature/genspark-astryx-redesign` (від `origin/main`, створена 2026-08-29).

## Мета

Усунути візуальну неузгодженість стилів у живому UI (aidrakon.tech), використовуючи Genspark Pro для генерації дизайну — **поверх існуючого Astryx-каркасу**, не заміняючи його. Причина рішення: логічні баги (Save→HTTP 500, `/agents` порожній, hardcoded `resolveTenant()`, англомовні сторінки) незалежні від стилю — повний редизайн з нуля їх не торкається і ризикує розсинхронізувати з tenancy/harness-логікою, яку Astryx-компоненти вже викликають. Йде паралельно з треком точкових правок плану (делеговано на .234, гілка `main`).

## Обсяг

**В межах:**
- Дизайн-токени (кольори, spacing, typography) для узгодженості між сторінками.
- Візуальний рескін існуючих Astryx-компонентів (не заміна framework).
- Виправлення конкретних style-невідповідностей, знайдених у живому UX-аудиті (окремі сторінки виглядають по-різному — точний перелік ще не в мене, з NAV_MAP.md/TEST_REPORT.md).

**Поза межами (свідомо):**
- Бекенд-логіка, tenancy, harness-specs, MCP-tooling — не чіпати.
- i18n runtime (укр/англ сторінки) — окрема P0-задача в корекції плану, не тут (хоча результат Genspark-дизайну має враховувати обидві мови в компонентах).
- HTTP 500 / `/agents` баги — окремий трек.

## Відкриті питання (потребують відповіді Q перед стартом реалізації)

1. Формат виводу Genspark — Figma-файл? CSS/design tokens JSON? Готові React-компоненти? Це визначає, як саме результат приземлиться в гілку.
2. Чи Genspark генерує з нуля дизайн-систему, чи приймає існуючий Astryx на вхід (screenshot/код) як базу для "фіксів стилю"?
3. Пріоритетні сторінки для першого проходу — весь UI одразу, чи почати з конкретних (worker onboarding, on-shift cycle — ті, що вже фігурують у workforce-vision плані)?

## Процес (чернетка, до уточнення п.1-3)

1. Q генерує дизайн у Genspark (зовнішній інструмент, поза цією сесією).
2. Експорт токенів/компонентів → `docs/plans/genspark-astryx-redesign/` (asset dump, аналогічно іншим research-папкам у репо).
3. Точкове застосування до конкретних Astryx-компонентів (CSS-змінні `--astryx-*` вже є в коді — SettingsPage.tsx використовує їх, ймовірно уся палітра централізована десь в одному місці; знайти через GitNexus перед правками).
4. Візуальна QA проти списку відомих style-невідповідностей.
5. PR з гілки в `main` — окремо від корекцій плану, або злиття координується вручну, якщо файли перетнуться.

## Координація з паралельним треком

Корекції плану (делеговано на .234, `main`) зараз в роботі. Ця гілка форкнута з `main` до завершення корекцій — після їх мержу треба буде `git rebase main` або `git merge main` в цю гілку, щоб не втратити.
