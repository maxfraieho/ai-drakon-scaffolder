# Фаза 4: Робота з помилками та геометрична валідація схем ДРАКОН

У цьому розділі ми розберемо інтелектуальну систему перевірки геометрії схем ДРАКОН перед тим, як вони будуть скомпільовані в код або передані ШІ-агентам. Ви дізнаєтеся, як працює функція валідації `convertDiagramToIrWithValidation()`, які бувають типи помилок і як вони візуалізуються в інтерфейсі користувача.

---

## 1. Концепція Геометричної Валідації

Мова ДРАКОН — це не просто набір картинок, а сувора математична система графічних правил (топології). Якщо користувач випадково з'єднає лінію не туди, залишить іконку «висіти в повітрі» або забуде вказати вихід для розгалуження, ШІ-агент не зможе правильно згенерувати код.

Для вирішення цієї проблеми ми розробили двоступеневий процес:
1. **Адаптація та Нормалізація:** Перетворення сирого JSON-формату редактора (`DrakonDiagram`) у канонічний формат проміжного представлення ШІ (`IrDiagram`).
2. **Детермінована Валідація:** Математичний аналіз структури графа за допомогою алгоритму пошуку в ширину (BFS) та правил топології ДРАКОН.

---

## 2. Як працює функція `convertDiagramToIrWithValidation()`

Ця функція є єдиною точкою входу для валідації схеми. Вона виконується автоматично кожного разу, коли ви зберігаєте схему або вносите в неї зміни.

```typescript
export function convertDiagramToIrWithValidation(diagram: DrakonDiagram): {
  ir: IrDiagram;
  issues: ValidationIssue[];
} {
  const conversionIssues: ValidationIssue[] = [];

  // Крок 1. Перевірка невідомих типів іконок
  for (const [id, item] of Object.entries(diagram.items)) {
    if (!IR_ITEM_TYPES.has(item.type as IrItemType)) {
      conversionIssues.push({
        code: "UNKNOWN_ITEM_TYPE",
        severity: "warning",
        message: `Unknown item type "${item.type}", mapped to "action"`,
        nodeId: id,
      });
    }
  }

  // Крок 2. Перетворення на плоский IR-список суміжності
  const ir = convertDiagramToIr(diagram);

  // Крок 3. Запуск детермінованого валідатора
  const { issues: validationIssues } = validateIrDeterministic(ir);

  // Крок 4. Злиття всіх виявлених зауважень
  return {
    ir,
    issues: [...conversionIssues, ...validationIssues],
  };
}
```

## 3. Які помилки знаходить система (Каталог Помилок)

Логіка `validateIrDeterministic` перевіряє схему на відповідність таким суворим критеріям:

### 3.1. Обов'язкові поля схеми (`SCHEMA_REQUIRED_FIELD`)
* **Опис:** Кожна схема повинна мати непусте ім'я (`name`) та містити принаймні кілька іконок всередині об'єкта `items`.
* **Наслідки:** Якщо поле пусте, схема вважається невалідною і не може бути скомпільована.

### 3.2. Неіснуючі зв'язки / Висячі лінки (`DANGLING_POINTER`)
* **Опис:** Виникає, коли лінк `one` або `two` вказує на `nodeId`, якого не існує в схемі. Це може статися при некоректному видаленні іконок.
* **Повідомлення:** `Node one points to missing node id: X`.
* **Критичність:** **ERROR (Критична помилка)**.

### 3.3. Недосяжні елементи алгоритму (`ORPHAN_NODE`)
* **Опис:** Використовуючи алгоритм пошуку в ширину (BFS) від стартової іконки, система будує шлях виконання. Будь-які іконки, які не потрапили у дерево обходу, вважаються «сиротами» (Orphans).
* **Повідомлення:** `Node is unreachable from the start node`.
* **Критичність:** **WARNING (Попередження)**. Можна виправити автоматично видаленням орфанів (`remove_orphan`).

### 3.4. Розірвані ланцюжки (`MULTIPLE_TERMINAL_CANDIDATE`)
* **Опис:** Будь-яка іконка (крім кінцевої іконки `end`), яка не має вихідного вектора `one` (наприклад, стрілка обривається), вважається кандидатом у термінальний вузол. В алгоритмі ДРАКОН має бути лише один кінець.
* **Повідомлення:** `Non-end node has no main vector (one) and should be merged`.
* **Критичність:** **WARNING**. Можна виправити автоматично злиттям терміналів (`merge_terminals`).

### 3.5. Некоректне розгалуження умови (`QUESTION_WITHOUT_BRANCH`)
* **Опис:** Іконка питання (`question` або `case`) повинна мати два напрямки виходу: `one` (для ТАК) та `two` (для НІ). Якщо вказано тільки один вихід, логіка розгалуження ламається.
* **Критичність:** **ERROR (Критична помилка)**.

## 4. Візуалізація помилок у Користувацькому Інтерфейсі (UI)

Коли функція повертає список `ValidationIssue[]`, ці дані миттєво відображаються під Canvas у вигляді **інтерактивної панелі помилок (Error Bar)**.

```
┌────────────────────────────────────────────────────────┐
│ Помилки схеми:                                         │
│ ⚠️ ORPHAN_NODE [id: 12]   ❌ DANGLING_POINTER [id: 4]   │
└────────────────────────────────────────────────────────┘
```

1. **Інтерактивні чіпси (Interactive Chips):** Кожна помилка малюється у вигляді маленької плашки (чіпса) з кольоровим кодуванням:
   * **Червоний колір:** Для критичних `ERROR` (наприклад, розірвана геометрія).
   * **Помаранчевий колір:** Для попереджень `WARNING` (недосяжні блоки).
2. **Миттєве фокусування (Click-to-Focus):** Кожна плашка містить ID іконки, яка викликала проблему (наприклад, `nodeId: 4`). Коли користувач натискає на чіпсу:
   * ID іконки автоматично копіюється в буфер обміну.
   * Система фокусує екран на відповідному елементі, підсвічуючи його, щоб ви могли миттєво стерти неправильний зв'язок або перепідключити лінію.
3. **Підказки (Tooltip):** При наведенні курсору на чіпсу з'являється розгорнута спливаюча підказка з детальним поясненням причини помилки простою людською мовою та технічним кодом помилки для розробників.

Завдяки такій глибокій інтеграції валідатора в інтерфейс, створення алгоритмів стає абсолютно безпечним: система ніколи не дозволить передати зламану геометрію на виконання ШІ-агенту.
