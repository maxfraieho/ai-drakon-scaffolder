# Фаза 5: Безпека, Авторизація та Деплоймент системи

У цьому розділі ми розберемо питання захисту даних, архітектуру авторизації між фронтендом та бекендом, а також принципи розгортання (deployment) нашої платформи на хмарній інфраструктурі **Cloudflare**.

---

## 1. Архітектура безпеки та роль `JWT_SECRET`

Наша платформа побудована як розподілена система (Decoupled Architecture):
* **Клієнтська частина (Frontend SPA):** Статичний додаток React, розміщений на Cloudflare Pages.
* **Брокер запитів (Cloudflare Worker):** Безсерверна (serverless) функція, яка виступає посередником (MCP Broker) та проксі-сервером.
* **Локальні ШІ-агенти:** Запущені на цільовому сервері розробника ( Fast-API мікросервіси на портах 8765-8767).

Щоб зловмисники не могли отримати доступ до локальних агентів або вашого хмарного сховища MinIO, використовується дворівнева схема захисту.

```
[React SPA Фронтенд] ──(JWT Token)──> [CF Worker Broker] ──(Bearer Token)──> [Локальні Агенти]
```

---

### 1.1. Авторизація клієнта через JWT
Кожен запит від браузера користувача до брокера Cloudflare Worker має містити заголовок авторизації `Authorization: Bearer <JWT_TOKEN>`.

* **Роль `JWT_SECRET`:** Це секретний ключ, який зберігається у змінних оточення (Environment Variables) нашого Cloudflare Worker. Клієнт при першому логіні отримує підписаний токен. Брокер використовує `JWT_SECRET` для миттєвої математичної перевірки валідності токена без необхідності запитів до бази даних.
* **Що всередині токена (Payload):**
  * `sub` (User ID / GitHub login): Канонічний ідентифікатор користувача.
  * `exp` (Expiration Time): Час життя токена (зазвичай 24 години). Після завершення терміну дії токен стає недійсним, і клієнт має повторно пройти автентифікацію.

```javascript
// Спрощений приклад перевірки токена всередині Cloudflare Worker
import { jwtVerify } from 'jose';

async function handleRequest(request, env) {
  const authHeader = request.headers.get("Authorization");
  if (!authHeader || !authHeader.startsWith("Bearer ")) {
    return new Response("Unauthorized: Missing Token", { status: 401 });
  }

  const token = authHeader.substring(7);
  try {
    // Верифікуємо токен за допомогою нашого секретного ключа
    const secret = new TextEncoder().encode(env.JWT_SECRET);
    const { payload } = await jwtVerify(token, secret);
    
    // Токен валідний, записуємо дані користувача в контекст запиту
    request.userId = payload.sub;
  } catch (err) {
    return new Response("Unauthorized: Invalid or Expired Token", { status: 403 });
  }
}
```

### 1.2. Авторизація між Брокером та Локальним сервером
Коли Cloudflare Worker переконався, що запит від клієнта легітимний, він проксіює його на IP-адресу вашого локального сервера (наприклад, `192.168.3.184` через захищений тунель code-proxy).

Для захисту цього каналу використовується **статичний Bearer Token** (за замовчуванням `drakon-mcp-2026`). Локальний сервер перевіряє цей токен у кожному вхідному HTTP-запиті. Якщо токен не збігається, запит миттєво відхиляється з кодом `401 Unauthorized`.

## 2. Безпека локального середовища розробки (Local Security Rules)

Під час розробки та запуску ШІ-агентів вкрай важливо дотримуватися правил гігієни безпеки, щоб випадково не злити приватні ключі у публічний доступ.

### 2.1. Використання файлу `.gitignore`
Ніколи не додавайте в комміти Git файли конфігурацій, що містять паролі, токени або приватні ключі. У нашому проекті такі файли автоматично додані в `.gitignore`:

* `config.json` — містить налаштування локального сервера та підключення.
* `.env` / `.env.local` — містять токени GitHub, паролі MinIO та секрети JWT.
* `entities.json` / `mempalace.yaml` — містять локальні індекси та шляхи до баз даних.

## 3. Деплоймент платформи (Deployment Guide)

Наша інфраструктура розгортається у хмарі Cloudflare, що забезпечує глобальну доступність та нульову вартість хостингу на безкоштовному тарифі (Free Tier).

### 3.1. Деплоймент Фронтенду (React SPA) на Cloudflare Pages
1. **Збірка проекту:** У корінь проекту виконується збірка за допомогою npm:
   ```bash
   npm run build
   ```
   Це генерує статичну оптимізовану папку `dist/`.
2. **Підключення до GitHub:** У панелі Cloudflare Pages виберіть ваш репозиторій `ai-drakon-scaffolder`.
3. **Налаштування збірки:**
   * Framework preset: `Vite`.
   * Build command: `npm run build` або `vite build`.
   * Build output directory: `dist`.
4. **Запуск:** Cloudflare автоматично збиратиме проект при кожному новому push у гілку `main` та публікуватиме його на домені `https://ai-drakon-scaffolder.pages.dev/`.

---

### 3.2. Деплоймент Брокера (Cloudflare Workers)
Брокер проксіює MCP-запити від Cloudflare Pages до локальних агентів.

1. **Конфігурація `wrangler.toml`:** У папці `cloudflare-worker/` розміщено конфігураційний файл для CLI-інструменту Wrangler:
   ```toml
   name = "drakon-mcp-broker"
   main = "src/index.ts"
   compatibility_date = "2026-05-26"

   [vars]
   # Нечутливі змінні оточення
   ENVIRONMENT = "production"
   ```
2. **Налаштування секретів:** Секретні змінні оточення, такі як `JWT_SECRET`, додаються виключно через панель керування Cloudflare або через CLI (вони шифруються та ніколи не потрапляють у відкритий код):
   ```bash
   npx wrangler secret put JWT_SECRET
   ```
3. **Публікація воркера:**
   ```bash
   npx wrangler deploy
   ```
   Воркер буде розгорнутий за адресою `https://drakon-mcp-worker.maxfraieho.workers.dev`.

Завдяки поєднанню **авторизації через JWT**, **захищених тунелів проксі** та **serverless архітектури Cloudflare**, наша система забезпечує максимальний рівень безпеки промислового класу при нульових витратах на інфраструктуру!
