# Фаза 1: Вступ у LangGraph з нуля — Концептуальний посібник для початківців

Ласкаво просимо до детального практичного посібника з **LangGraph**! Цей матеріал створено спеціально для того, щоб допомогти розібратися в сучасних архітектурах ШІ-агентів, навіть якщо ви тільки починаєте свій шлях у розробці систем на базі великих мовних моделей (LLM).

---

## 1. Лінійні ланцюжки (LangChain) проти Циклічних графів (LangGraph)

Щоб зрозуміти цінність LangGraph, спершу згадаємо, як будуються базові програми з ШІ за допомогою стандартних ланцюжків (наприклад, у класичному LangChain).

### Обмеження лінійних ланцюжків (LangChain)
У класичних LLM-додатках розробка нагадує конвеєр:
1. Отримати запит користувача.
2. Сформувати промпт.
3. Надіслати в LLM.
4. Обробити результат парсером.
5. Передати наступному кроку.

```
[Запит Користувача] ──> [Промпт] ──> [Мовна Модель] ──> [Парсер] ──> [Фінальна Відповідь]
```

Це чудово працює для простих завдань (наприклад, перекласти текст або структурувати JSON). Проте реальний світ набагато складніший. Що робити, якщо:
* ШІ-модель припустилася помилки у виклику функції (Tool Call)?
* Згенерований код містить синтаксичну помилку?
* Користувач попросив внести зміни в раніше згенеровану відповідь?

У лінійному конвеєрі немає шляху назад. Ви не можете змусити модель виправити власну помилку, оскільки рух відбувається тільки вперед.

### Циклічний підхід LangGraph
**LangGraph** — це спеціалізована бібліотека, побудована поверх екосистеми LangChain, яка перетворює лінійний конвеєр на **орієнтований граф**, що може містити **цикли (петлі зворотного зв'язку)**.

```
                   ┌───────────────────────┐
                   ▼                       │ (Помилка валідації)
[Старт] ──> [Агент (LLM)] ──> [Валідатор коду] ──> [Успіх] ──> [Фінал]
```

Завдяки циклам ми отримуємо можливість реалізувати патерн **«Агент-Редактор»**:
1. Модель генерує рішення.
2. Інший вузол (наприклад, локальний компілятор чи лінтер) перевіряє роботу моделі.
3. Якщо знайдено помилку, граф направляє потік керування назад до моделі разом із текстом помилки.
4. Модель аналізує свій факап і випускає оновлену версію.

Цей процес може повторюватися доти, доки критерій якості не буде повністю виконано. Це і є ключова відмінність: **агенти стають здатними до самокорекції та автономного вирішення складних завдань**.

## 2. Три кити LangGraph: Стан, Вузли та Ребра

Архітектура будь-якого графа в LangGraph тримається на трьох фундаментальних концепціях. Давайте детально розберемо кожну з них.

### 2.1. Стан (State)
**Стан (State)** — це спільна пам'ять вашого графа. Це єдине джерело правди (Single Source of Truth), яке передається від одного кроку до іншого.

* **Як це влаштовано:** Технічно Стан описується як звичайний клас на базі `TypedDict` (у Python) або типізованого об'єкта. У ньому зберігаються змінні, які потрібні вузлам для роботи: історія повідомлень, проміжні результати парсингу, лічильники циклів, статус виконання тощо.
* **Концепція Редукторів (Reducers):** Коли вузол оновлює стан, він не просто перезаписує його повністю. Ми можемо визначити спеціальні правила злиття (reducers). Наприклад, для списку повідомлень ми вказуємо `operator.add`. Це означає, що нові відповіді моделі будуть автоматично дописуватися в кінець списку повідомлень, зберігаючи всю історію діалогу, замість того щоб затирати старі репліки.

```python
from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages

# Визначаємо структуру спільної пам'яті нашого графа
class AgentState(TypedDict):
    # Анотація add_messages вказує редуктор: нові повідомлення додаються до списку
    messages: Annotated[list, add_messages]
    # Додаткові змінні стану
    code_snippet: str
    is_valid: bool
    attempt_count: int
```

---

### 2.2. Вузли (Nodes)
**Вузли (Nodes)** — це виконавчі органи графа. Це кроки, на яких безпосередньо виконується логіка програми.

* **Що є вузлом:** Будь-яка функція на Python (синхронна або асинхронна), яка відповідає інтерфейсу: приймає поточний `State` і повертає **словник з оновленими полями стану**.
* **Різноманіття вузлів:** Вузлом може бути як виклик великої мовної моделі (агент), так і повністю детермінований код (наприклад, виконання регулярного виразу, запит до бази даних або запуск компілятора Python).

```python
# Приклад вузла, який викликає мовну модель для написання коду
def code_generator_node(state: AgentState):
    print(f"--- ГЕНЕРАЦІЯ КОДУ (Спроба №{state['attempt_count'] + 1}) ---")
    
    # Дістаємо останнє повідомлення (запит користувача)
    user_query = state["messages"][-1].content
    
    # Викликаємо модель (LLM)
    response = llm.invoke(f"Напиши код на Python для: {user_query}")
    
    # Повертаємо словник з оновленнями стану. 
    # Поля з цього словника автоматично зіллються з глобальним станом графа!
    return {
        "messages": [response],
        "code_snippet": response.content,
        "attempt_count": state["attempt_count"] + 1
    }
```

---

### 2.3. Ребра (Edges)
**Ребра (Edges)** визначають напрямок руху (потік керування) між вузлами. Вони з'єднують вузли в єдиний робочий процес.

Існує два типи ребер:
1. **Звичайні ребра (Normal Edges):** Жорстко задають безумовний перехід від вузла А до вузла Б. Як тільки закінчує виконуватися вузол А, керування автоматично переходить до вузла Б.
2. **Умовні ребра (Conditional Edges):** Забезпечують динамічне розгалуження (маршрутизацію) в залежності від поточного Стану.

Для побудови умовного ребра ми пишемо спеціальну **маршрутизуючу функцію (router function)**. Вона аналізує поточний Стан і повертає ім'я наступного вузла, до якого слід перейти.

```python
# Маршрутизатор: вирішує, чи потрібно йти на коло виправлення помилок
def routing_decision_edge(state: AgentState):
    # Якщо код валідний, ми можемо завершити виконання
    if state["is_valid"]:
        return "end_node"
    
    # Якщо кількість спроб вичерпана, ми також зупиняємося, щоб не піти в нескінченний цикл
    if state["attempt_count"] >= 3:
        print("!!! Досягнуто ліміту спроб виправлення коду !!!")
        return "end_node"
    
    # Якщо є помилки і спроби не вичерпані — повертаємося до генератора для самокорекції
    return "code_generator_node"
```

## 3. Збірка та компіляція графа

Після того як ми описали Стан, створили функції-вузли та маршрутизатори, ми об'єднуємо все це за допомогою конструктора `StateGraph` та компілюємо граф.

```python
from langgraph.graph import StateGraph, START, END

# 1. Створюємо конструктор графа, передаючи йому клас нашого Стану
workflow = StateGraph(AgentState)

# 2. Реєструємо всі вузли в системі
workflow.add_node("code_generator_node", code_generator_node)
workflow.add_node("validator_node", validator_node) # Додатковий вузол валідації коду

# 3. Вказуємо точку входу в граф
workflow.add_edge(START, "code_generator_node")

# 4. Вказуємо перехід від генератора до валідатора
workflow.add_edge("code_generator_node", "validator_node")

# 5. Додаємо розумне умовне ребро на виході з валідатора
workflow.add_conditional_edges(
    "validator_node",
    routing_decision_edge, # Наша функція маршрутизації
    {
        "code_generator_node": "code_generator_node", # Якщо повернуло це ім'я -> переходимо назад
        "end_node": END                              # Якщо повернуло 'end_node' -> закінчуємо граф
    }
)

# 6. Компілюємо граф. Тепер він готовий приймати запити!
app = workflow.compile()
```

Ця проста та елегантна структура лежить в основі нашого проекту. Завдяки розумінню цих трьох елементів — **Стану, Вузлів та Ребер** — ви тепер можете вільно орієнтуватися в роботі будь-яких автономних ШІ-агентів, побудованих на LangGraph!
