# 0004. Використовувати MemPalace на базі ChromaDB для семантичної пам'яті сесій, щоденників та контексту розробки

## Контекст і формулювання проблеми
Під час розробки та функціонування `ai-drakon-scaffolder` накопичується значний обсяг знань: логи тривалих сесій взаємодії, щоденники розробки (development diaries), архітектурні інсайти та контекст прийнятих рішень. 

При перезапуску агентів або переході до нових завдань весь робочий контекст втрачається, якщо зберігати його лише в оперативній пам'яті чи плоских текстових файлах. Звичайні сховища не дозволяють агенту формулювати запити природною мовою та швидко знаходити відповідні прецеденти з минулих сесій за змістом, а не за точним збігом ключових слів.

## Рушії рішення
- **Довготривала семантична пам'ять**: Збереження логів сесій, щоденників (diaries) та контексту розробки між сеансами роботи.
- **Семантичний пошук та буст валідності**: Можливість знаходити концептуально схожі рішення та піднімати релевантний контекст за допомогою векторних ембедінгів.
- **Структурована організація знань**: Підтримка концепції "палацу пам'яті" (крила, кімнати, ящики / wings, rooms, drawers) для ієрархічної класифікації контексту.

## Розглянуті варіанти
1. **MemPalace (на базі векторної БД ChromaDB)** (обраний варіант)
2. **Реляційні бази даних або файлові об'єктні сховища (PostgreSQL / MinIO S3)** (альтернатива з таблиці)
3. **Хмарні векторні сервіси (Pinecone / Qdrant Cloud)** (додатковий розглянутий варіант для повноти)

## Підсумок рішення
Обрано **MemPalace** з використанням локальної векторної бази даних **ChromaDB** як підсистему семантичної пам'яті для збереження сесій, щоденників розробки та контексту прийняття рішень.

### Наслідки
- **Позитивні:**
  - ШІ-агенти можуть виконувати пошук за змістом запиту серед сотень попередніх сесій та нотаток.
  - Зменшення витрат токенів завдяки вибірковій загрузці тільки релевантних фрагментів знань (retrieval-augmented workflow).
  - Повна автономність і локальний контроль над векторною базою без залежності від платних хмарних векторних API.
- **Негативні:**
  - Необхідність обчислення векторних ембедінгів при додаванні нових записів.
  - Потреба у валідації та періодичній інвалідації застарілих векторних даних (knowledge invalidation).
  - Додаткове використання дискового простору та ресурсів процесора для роботи ChromaDB.

## Плюси і мінуси варіантів

### MemPalace (ChromaDB)
* Добре: Вбудована підтримка векторного пошуку на базі ембедінгів безпосередньо в середовищі розробки.
* Добре: Зручна таксономія ("крила", "кімнати", "щоденники") для швидкої фільтрації знань.
* Добре: Готові MCP-інструменти (`mempalace_search`, `mempalace_diary_read`, `mempalace_kg_query`).
* Погано: Локальне збереження вимагає синхронізації при роботі на кількох машинах.
* Погано: Обмежена продуктивність при екстремально великих обсягах векторів у порівнянні з розподіленими кластерами.

### Реляційні бази даних / S3 (PostgreSQL / MinIO S3)
* Добре: Надійне транзакційне збереження сирих логів, тексту та бінарних артефактів.
* Добре: Проста організація за датою та ідентифікатором сесії.
* Погано: Відсутність нативного семантичного векторного пошуку (без сторонніх плагінів типу pgvector).
* Погано: Неможливість ефективно ранжувати релевантність концептуальних описів за природномовним запитом.

### Хмарні векторні бази (Pinecone / Qdrant Cloud)
* Добре: Висока швидкість індексації, керована масштабованість, SLA доступності.
* Добре: Автоматичний бекап та хмарний веб-інтерфейс моніторингу.
* Погано: Додаткова фінансова вартість за зберігання та виклики API.
* Погано: Залежність від зовнішнього мережевого з'єднання та ризик витоку конфіденційного контексту розробки.

## Додаткова інформація
Інструменти MemPalace інтегровані через MCP-сервер (`mempalace`), забезпечуючи запис та зчитування щоденників сесій (`mempalace_diary_write`, `mempalace_diary_read`), а також ведення графу знань проєкту.
