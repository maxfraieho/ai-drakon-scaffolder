# 0003. Використовувати GitNexus для семантичного графу коду та розрахунку blast radius змін

## Контекст і формулювання проблеми
Автоматизована генерація, модифікація та рефакторинг коду за допомогою ШІ-агентів у проєкті `ai-drakon-scaffolder` несе ризик виникнення прихованих регресій. При зміні сигнатур функцій, інтерфейсів схем ДРАКОН або внутрішніх модулів агент повинен чітко розуміти повну топологію залежностей проєкту. 

Традиційний текстовий пошук по кодовій базі не враховує семантику мови програмування (AST, ланцюжки викликів, спадкування, імпорти/експорти), через що агент або пропускає залежні модулі, або завантажує занадто багато нерелевантного контексту у вікно моделі.

## Рушії рішення
- **Точний розрахунок Blast Radius**: Можливість математично визначити радіус впливу планованої зміни до початку редагування файлів.
- **Глибокий семантичний аналіз зв'язків**: Побудова графу кодової бази, який відображає виклики функцій, використання типів і структурні залежності.
- **Підтримка структурованих запитів для агентів**: Можливість виконання точкових Cypher-запитів та навігації по коду через стандартизовані MCP-інструменти.

## Розглянуті варіанти
1. **GitNexus** (обраний варіант)
2. **Стандартний текстовий grep / ripgrep** (альтернатива з таблиці)
3. **LSP (Language Server Protocol) сервери через CLI-інструменти** (додатковий розглянутий варіант для повноти)

## Підсумок рішення
Обрано **GitNexus** як інструмент побудови та аналізу семантичного графу знань кодової бази для оцінки blast radius змін та надання структурного контексту ШІ-агентам.

### Наслідки
- **Позитивні:**
  - ШІ-агенти отримують точний контекст викликів і залежностей, що різко знижує кількість регресій при кодогенерації.
  - Можливість автоматичного аналізу впливу змін перед збереженням або фіксацією коду.
  - Наявність спеціалізованого набору MCP-інструментів (`query`, `cypher`, `impact`, `context`, `detect_changes`) для швидкого дослідження структури.
- **Негативні:**
  - Необхідність періодичної переіндексації графу коду при суттєвих змінах файлової структури.
  - Додаткові вимоги до пам'яті та дискового простору для збереження графового індексу.
  - Залежність від підтримки конкретних синтаксичних конструкцій парсером GitNexus.

## Плюси і мінуси варіантів

### GitNexus
* Добре: Спеціалізований для аналізу архітектурних зв'язків та оцінки радіусу впливу (blast radius).
* Добре: Підтримує потужну графову мову запитів (Cypher) для пошуку складних ланцюжків залежностей.
* Добре: Безшовна інтеграція з AI-агентами через протокол MCP.
* Погано: Потребує етапу попередньої індексації проєкту.
* Погано: Менш відомий інструмент у порівнянні з класичними Unix-утилітами.

### Стандартний текстовий grep / ripgrep
* Добре: Працює миттєво без створення додаткових індексів та баз даних.
* Добре: Універсальний, доступний у будь-якому терміналі та середовищі.
* Погано: Повна відсутність контексту синтаксичного дерева (AST) та зв'язків між викликами функцій.
* Погано: Велика кількість хибнопозитивних або хибнонегативних результатів при збігу імен змінних/методів.
* Погано: Не здатний розрахувати непрямий каскадний вплив (transitive impact) змін.

### LSP (Language Server Protocol) через CLI (наприклад, tsserver/pyright)
* Добре: Максимально точна типізація та резолвінг посилань безпосередньо від компілятора мови.
* Добре: Підтримка операцій `find-references`, `go-to-definition`, `rename`.
* Погано: Висока складність оркестрації окремих LSP для багатомовних кодових баз через CLI.
* Погано: Відсутність зручного вбудованого механізму графового аналізу транзитивного blast radius та виконання декларативних аналітичних запитів.

## Додаткова інформація
GitNexus підключений через MCP-сервер і активно використовується перед етапами рефакторингу та автоматизованого оновлення коду в `ai-drakon-scaffolder` для захисту цілісності схеми та API.
