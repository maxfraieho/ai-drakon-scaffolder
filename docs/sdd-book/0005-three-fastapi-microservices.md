# 0005. Три окремі FastAPI-мікросервіси замість монолітного бекенду

## Контекст і формулювання проблеми

Проєкт `ai-drakon-scaffolder` складається з трьох спеціалізованих агентських підсистем:
1. Генератор DRAKON-схем за синтаксичним деревом (AST) та валідатор IR (`drakon-agent`).
2. Оркестратор складних мультиагентних LangGraph-пайплайнів та сесій розробки (`architect-agent`).
3. Документаційний агент з інтеграцією Obsidian-нотаток, DQL-запитів та Git-синхронізації (`docs-agent`).

Постало архітектурне питання: організувати бекенд як єдиний монолітний FastAPI-додаток (на одному порту зі спільним життєвим циклом) чи розділити його на 3 незалежні автономні FastAPI-процеси зі своїми виділеними портами (`8765`, `8766`, `8767`).

**Перевірка проти чекліста ADR-значущості (`constitution.md` §3.1):**
1. **Вплив на NFR**: повна ізоляція збоїв (падіння LangGraph-пайплайна або DQL-парсера не зупиняє генерацію DRAKON IR), незалежне споживання пам'яті, паралельний запуск.
2. **Ціна відкату**: висока (злиття 3 процесів вимагає переписування маршрутизації фронтенду, адаптації middleware, усунення конфліктів у `sys.path`, переробки lifespan-контекстів).
3. **2+ реальних альтернативи**: монолітний FastAPI з модульними роутерами, ASGI multi-app dispatcher під одним портом.
4. **Чіткі межі підсистем**: AST-трансляція, агентна оркестрація, документування бази знань.
5. **Нові системні інваріанти**: виділені порти `8765/8766/8767`, обов'язкові контракти `GET /health` і `GET /settings`, автономні життєві цикли.

Відповідає щонайменше 4 з 5 критеріїв — ADR обов'язковий.

## Рушії рішення

- **Fault Tolerance**: генерація та валідація DRAKON-схем (`drakon-agent`) — критичне ядро системи, має працювати незалежно від експериментальних агентних пайплайнів чи помилок Git-блокувань під час запису документації.
- **Різний профіль навантаження та стан**: `drakon-agent` — переважно stateless-транслятор; `architect-agent` тримає сесії виконання в пам'яті (`_sessions`, `BUILD_STORE`); `docs-agent` виконує блокуючі системні виклики `git commit/push` та файловий I/O.
- **Гнучкість розробки та конфігурації**: незалежний перезапуск, різні LLM-проксі моделі через власні `.env` для кожного агента.

## Розглянуті варіанти

1. **Три окремі FastAPI-процеси на портах 8765/8766/8767** (обраний варіант)
2. **Монолітний FastAPI-сервіс зі спільним `main.py`**
3. **Єдиний ASGI Server з mount sub-applications** (`app.mount("/drakon", ...)` тощо)

## Підсумок рішення

Обрано **Варіант 1**: архітектура з трьох незалежних FastAPI-мікросервісів, кожен — окремий Python-процес зі своїм портом.

### Наслідки
- **Позитивні:**
  - Висока стабільність базового транслятора `drakon-agent` — не залежить від збоїв інших агентів.
  - Незалежний тюнінг, виділення ресурсів та оновлення версій кожного агента.
  - Проста модель зневадження кожного сервісу окремо.
- **Негативні:**
  - Потрібно підтримувати спільний контракт для `/health` та `/settings`.
  - Фронтенд-клієнт мусить знати про конфігурацію трьох портів (`8765`, `8766`, `8767`) або використовувати проксі.
  - Три окремі процеси для моніторингу/запуску замість одного.

## Плюси і мінуси варіантів

### Варіант 1: Три окремі FastAPI-процеси (обраний)
* Добре: повна ізоляція пам'яті, процесорного часу, середовища виконання.
* Добре: збій одного агента (OOM, зависання підпайплайна) не зачіпає інші.
* Добре: фронтенд звертається до кожного сервісу напряму без API Gateway на етапі локальної розробки.
* Погано: три окремих процеси для моніторингу/запуску, три зайняті порти.

### Варіант 2: Монолітний FastAPI-сервіс
* Добре: один процес, один порт, один файл конфігурації.
* Погано: відсутність ізоляції збоїв — фатальна помилка в LangGraph-воркері кладе весь бекенд.
* Погано: конфлікти глобальних змінних та стану (напр. конфігурація proxy/memory), конфлікти в `sys.path`.

### Варіант 3: Єдиний ASGI Server з mount sub-applications
* Добре: єдиний вхідний порт при частковій ізоляції роутерів.
* Погано: спільний event-loop і спільний процес Python — блокуючі операції в `docs-agent` (Git I/O) блокують обробку запитів у `drakon-agent`.

## Додаткова інформація

Контракти портів та обов'язкових ендпоінтів зафіксовані у `specs/001-backend-agents-baseline/spec.md`. Відповідні змінні середовища задаються у файлах `.env` відповідних каталогів `services/*`.
