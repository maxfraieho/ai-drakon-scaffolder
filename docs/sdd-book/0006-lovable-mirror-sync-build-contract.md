# 0006. Утримувати дзеркало `src/` і `.lovable/src/` для Cloudflare Pages

## Контекст і формулювання проблеми

Розробка використовує `src/` як dev source, але Cloudflare Pages збирає застосунок із `.lovable/`. Це створює межу між робочим checkout і production build: зміна лише в `src/` може бути невидимою для деплою. F2 показав наслідок такого drift: на commit `9c7e01bf` `src/routeTree.gen.ts` не був регенерований після `97990862`.

## Рушії рішення

* детермінований production build;
* відсутність розбіжностей між локальною розробкою та Cloudflare Pages;
* сумісність із baseline invariant 2.

## Розглянуті варіанти

* дзеркальна синхронізація перед комітом;
* збірка безпосередньо з `src/`;
* ручне копіювання вибраних файлів.

## Підсумок рішення

Обрано дзеркальну синхронізацію: `src/` є dev source, `.lovable/src/` — build-контракт Cloudflare Pages. Перед комітом після змін у `src/` агент виконує `rsync -av --delete src/ .lovable/src/`.

### Наслідки

* Добре: production бачить повний ідентичний frontend checkout.
* Добре: `--delete` прибирає застарілі файли та робить drift помітним.
* Погано: коміти містять дзеркальні зміни й потребують перевірки парності.

## Плюси і мінуси варіантів

### Дзеркальна синхронізація

* Добре: відповідає фактичному Cloudflare Pages pipeline.
* Погано: потрібен обов’язковий крок перед комітом.

### Збірка з `src/`

* Добре: немає дубльованого дерева.
* Погано: суперечить поточному deploy-контракту й потребує зміни Cloudflare Pages.

### Ручне копіювання

* Добре: мало інструментальних вимог.
* Погано: легко пропустити файл або залишити stale mirror.

## Додаткова інформація

Джерело правила: `specs/000-baseline/spec.md` інваріант 2. Парність generated route tree уточнена в ADR-0007.
