# Контекстний пошук для агентів: дослідження варіантів

Цей звіт містить дослідження можливостей контекстного пошуку по документації проекту (74 `.md` файлів, загальним обсягом ~500KB тексту) для AI-агентів системи `AI-DRAKON`. Оскільки сервіс `MemPalace` (який використовує зовнішню ChromaDB) є занадто важким для запуску на Termux, ми аналізуємо легші альтернативи (in-project, lightweight), що вже інтегровані в систему або можуть бути просто додані.

---

## 1. Поточний стан (що вже є в проекті)

На основі детального аналізу вихідного коду, у проекті вже існують дві локальні реалізації Knowledge Base (KB) на основі алгоритму BM25:

1. **Crisis-Bot (`services/crisis-bot/knowledge_base/`)**:
   - **Алгоритм**: `BM25Plus` з бібліотеки `rank_bm25`.
   - **Сегментація**: Розбиває markdown-файли на секції за допомогою заголовків другого рівня `## `.
   - **Токенізація**: Регулярний вираз `[a-zA-Zа-яА-ЯіІїЇєЄёЁ0-9_]+`, що підтримує як англійські, так і кириличні (українські/російські) символи.
   - **Режим роботи**: Singleton. Ініціалізується при запуску шляхом сканування директорії знань.

2. **Drakon-Agent (`services/drakon-agent/knowledge_base/`)**:
   - **Алгоритм**: `BM25Okapi` з бібліотеки `rank_bm25`.
   - **Сегментація**: Аналогічне розбиття на секції за `## `.
   - **Токенізація**: Регулярний вираз `[a-zA-Z0-9_]+`, що підтримує лише англійські символи (ігнорує кирилицю).
   - **Режим роботи**: Singleton.

### Перенесення в `services/shared/`
Обидві реалізації є надзвичайно схожими і можуть бути об'єднані та перенесені у спільну бібліотеку `services/shared/drakon_shared` (або `services/shared/kb_client.py`). Уніфікований клієнт повинен використовувати розширену токенізацію (з кирилицею) та надавати можливість вибору між `BM25Okapi` та `BM25Plus`.

## 2. Оцінка варіантів

Для обробки 74 `.md` файлів обсягом ~500KB проведено оцінку чотирьох варіантів:

| Варіант | RAM | Пошук (ms) | Складність реалізації | Semantic? | Плюси | Мінуси |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **ВАРІАНТ A**: `rank-bm25` | ~5 MB | ~50 ms | Дуже низька (вже використовується в проекті) | Ні (Keyword) | Вже встановлено, чистий Python, не потребує сервера чи БД, швидкий. | Лише пошук за ключовими словами, потребує повторного побудови індексу в оперативній пам'яті при кожному старті (хоча для 74 файлів це займає <50ms). |
| **ВАРІАНТ B**: `SQLite FTS5` | ~2 MB | ~10 ms | Низька (вбудовано в stdlib Python) | Ні (Keyword / Full-text) | Нульові залежності (stdlib), надзвичайно швидкий, підтримує складні логічні запити (AND, OR, NOT, MATCH), персистентність з коробки. | Лише пошук за точним збігом слів, потребує створення схеми віртуальної таблиці. |
| **ВАРІАНТ C**: `ai-memory` | ~30 MB (клієнт) | ~20 ms | Середня (HTTP MCP-клієнт) | Так (RRF з графом) | Готовий Docker-контейнер, підтримує RRF (Reciprocal Rank Fusion), враховує контекст сесій, має зручний MCP інтерфейс. | Потребує постійно запущеного Docker-сервісу, для нашої документації наразі містить 0 сторінок (орієнтований на сесії, а не на статичну KB). |
| **ВАРІАНТ D**: `ChromaDB` (local) | ~300 MB | ~150 ms | Висока (потребує C++ білдів у Termux) | Так (Vector semantic) | Справжній семантичний пошук, розуміння синонімів та контексту. | Дуже важкий, велике споживання RAM, проблеми з компіляцією залежностей на мобільних пристроях / Termux. |

## 3. Рекомендація + обґрунтування

> [!TIP]
> **Рекомендований вибір: Гібридний підхід (Варіант B: SQLite FTS5 як основний, або Варіант A: rank-bm25 для повної сумісності)**

**Обґрунтування**:
1. **SQLite FTS5** є найкращим довгостроковим рішенням для lightweight in-project пошуку. Він вбудований у стандартну бібліотеку Python `sqlite3`, не потребує встановлення жодних додаткових pip-пакетів і споживає мінімум оперативної пам'яті (~2MB). Завдяки токенізатору `unicode61` він чудово працює з українською мовою з коробки.
2. Проте, оскільки **Варіант A (`rank-bm25`)** вже інтегровано в декілька сервісів проекту, найшвидшим кроком для уніфікації є об'єднання поточних напрацювань у `services/shared/` з додаванням кириличної токенізації.
3. Ми пропонуємо створити уніфікований `kb_client.py`, який може працювати як в in-memory режимі на базі SQLite FTS5 (швидкість, гнучкість запитів), так і використовувати BM25.

## 4. Прототип `shared/kb_client.py` (на основі SQLite FTS5)

Нижче наведено мінімальний та ефективний прототип уніфікованого клієнта знань на базі вбудованого `sqlite3` та FTS5:

```python
import sqlite3
import re
from pathlib import Path

class KBClient:
    def __init__(self, db_path: str = ":memory:"):
        self.conn = sqlite3.connect(db_path)
        # Створюємо віртуальну FTS5 таблицю з підтримкою unicode61 для кирилиці
        self.conn.execute("""
            CREATE VIRTUAL TABLE IF NOT EXISTS kb 
            USING fts5(source, heading, content, tokenize="unicode61 tokenchars '/_-'")
        """)

    def index_documents(self, docs_dir: Path) -> None:
        """Зчитує всі .md файли, ділить на секції ## та індексує."""
        with self.conn:
            self.conn.execute("DELETE FROM kb")  # Очищення старого індексу
            for md in sorted(docs_dir.glob("*.md")):
                text = md.read_text(encoding="utf-8")
                sections, heading, lines = [], "intro", []
                for line in text.splitlines():
                    if line.startswith("## "):
                        if lines:
                            sections.append((heading, "\n".join(lines).strip()))
                        heading, lines = line[3:].strip(), []
                    else:
                        lines.append(line)
                if lines:
                    sections.append((heading, "\n".join(lines).strip()))
                
                for head, content in sections:
                    if content.strip():
                        self.conn.execute(
                            "INSERT INTO kb(source, heading, content) VALUES (?, ?, ?)",
                            (md.name, head, content)
                        )

    def search(self, query: str, top_k: int = 5) -> list[dict]:
        """Швидкий повнотекстовий пошук з сортуванням за релевантністю."""
        # Очищення запиту від спеціальних символів FTS5 для запобігання синтаксичних помилок
        clean_query = re.sub(r'[^\w\s\-\/\_]', ' ', query).strip()
        if not clean_query:
            return []
        
        cursor = self.conn.execute("""
            SELECT source, heading, content, rank 
            FROM kb 
            WHERE kb MATCH ? 
            ORDER BY rank 
            LIMIT ?
        """, (clean_query, top_k))
        
        return [
            {
                "source": row[0],
                "heading": row[1],
                "content": row[2],
                "score": round(-float(row[3]), 4)  # rank в FTS5 менший = кращий, тому міняємо знак
            }
            for row in cursor.fetchall()
        ]
```

## 5. `ai-memory`: чи підходить як context store? Висновок

Під час дослідження сервісу `ai-memory`, що запущений на хості `192.168.3.184:49374`, було встановлено наступне:

- **База даних**: Використовує SQLite з таблицями `pages`, `pages_fts` (FTS5 з токенізатором `unicode61 tokenchars '/_-'`) та `observations_fts`. Тобто, технологічно `ai-memory` вже містить усередині повнотекстовий пошук FTS5.
- **API доступність**: 
  - Ендпоінти `/wiki/search` та `/wiki/pages` повертають `404 Not Found`, оскільки веб-інтерфейс змонтовано за префіксом `/web`.
  - Повнотекстовий пошук доступний людині через браузер за адресою `http://192.168.3.184:49374/web/search?q=<запит>`.
  - Для агентів основний інтерфейс взаємодії — це **MCP (Model Context Protocol)** сервер, що приймає POST-запити на шлях `/mcp`. Ми успішно протестували виклик методу `memory_query` через JSON-RPC POST-запит з обов'язковим заголовком `Accept: application/json, text/event-stream`.
- **Висновок щодо придатності**:
  - `ai-memory` є **ідеальним** інструментом для довготривалої пам'яті сесій, збереження спостережень та передачі стану між агентами (handoffs).
  - Проте, для пошуку по статичній документації проекту (74 `.md` файли) він є **надлишковим**, оскільки наразі містить 0 сторінок у проектах і вимагає постійної синхронізації файлів у Docker-контейнер.
  - Рекомендується використовувати `ai-memory` виключно як сесійний context store, а для пошуку по документації використовувати вбудований у клієнт `SQLite FTS5` (Варіант B).
