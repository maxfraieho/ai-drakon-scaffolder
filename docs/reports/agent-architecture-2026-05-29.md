# Архітектура агентів: поточний стан та пропозиція уніфікації

Цей звіт містить глибокий аналіз архітектури трьох основних AI-агентів системи `AI-DRAKON` (`architect-agent`, `docs-agent`, `drakon-agent`), виявляє дублювання компонентів, описує унікальну логіку кожного з них та пропонує стратегію уніфікації під один спільний фреймворк із залученням спільної пам'яті.

---

## 1. Поточна архітектура

На основі аналізу вихідного коду та конфігураційних файлів трьох агентів, поточний стан їхньої архітектури зведено у наступну таблицю:

| Агент | Framework | LLM-клієнт | Knowledge Base (KB) | Memory |
| :--- | :--- | :--- | :--- | :--- |
| **Architect Agent** (порт `8766`) | FastAPI (Python) | `httpx.post` до `/chat/completions` (OpenAI format, default model: `fast-proxy`) | Зчитує перші 2000 символів з `00-drakon-rules.md` (назва та типи вузлів), кешує в пам'яті як string snippet | Використовує спільний `memory_manager.py` (local/GitHub) під простором імен `architect` (`MEMORY.md`) |
| **Docs Agent** (порт `8767`) | FastAPI (Python) | `httpx.post` до `/chat/completions` (OpenAI format, default model: `coding-proxy`) | Відсутня в загальному чаті (отримує як вхідний `kb_context` у деяких API) | Використовує спільний `memory_manager.py` під простором імен `docs` (`MEMORY.md`) |
| **Drakon Agent** (порт `8765`) | FastAPI (Python) | `httpx.post` до `/chat/completions` (OpenAI format, default model: `coding-proxy` для refiner, `agent-proxy` для чату) | Токен-орієнтоване BM25 індексування (`BM25Okapi` з `rank_bm25`). Індексує файли в директорії `knowledge/` | Має модуль `memory_manager.py` (який імпортують інші агенти), але сам не використовує `MEMORY.md` у чаті чи аналізі |

---

## 2. Спільні компоненти (дублювання)

Аналіз коду показує значний рівень дублювання логіки між агентами:

1. **LLM-клієнт**:
   - І `architect_chat.py`, і `docs_chat.py`, і `refiner.py` реалізують власний клієнт через HTTP-запити за допомогою бібліотеки `httpx` до OpenAI-сумісного проксі (`{PROXY_URL}/chat/completions`).
   - Логіка обробки заголовків, авторизації (`Bearer {PROXY_TOKEN}`), таймаутів (60.0–90.0 секунд) та витягування відповідей (`choices[0].message.content`) повторюється майже один-в-один.
2. **FastAPI інфраструктура**:
   - Усі три агенти розгорнуті як окремі мікросервіси на FastAPI з подібною CORS конфігурацією, обробкою помилок та структурами моделей Pydantic (наприклад, `ChatRequest`).
3. **Керування Пам'яттю**:
   - `architect-agent` та `docs-agent` імпортують `memory_manager.py` безпосередньо з директорії `drakon-agent` (шляхом динамічного додавання `sys.path.append`). Це створює пряму файлову залежність між сервісами.

---

## 3. Унікальна логіка кожного агента

Кожен агент виконує спеціалізовану роль із застосуванням унікальних технологій:

*   **Architect Agent**:
    - Орієнтований на глобальне розуміння проекту (керування файловим деревом, генерація ієрархій алгоритмів).
    - Містить унікальні роутери для побудови конфігурацій конвеєрів виконання (`pipeline_route.py`, `graph_pipeline_route.py`).
*   **Docs Agent**:
    - Спеціалізується на генерації Obsidian-сумісної документації для окремих бізнес-модулів (секція `/document`).
    - Має вбудований Git-клієнт (`_git_save`), який після генерації документації автоматично виконує `pull --rebase`, `add`, `commit` та `push` для синхронізації з репозиторієм.
*   **Drakon Agent**:
    - Найбільш технічно складний сервіс. Виконує AST-аналіз коду на Python (через `PythonAnalyzer`) та JS/TS (через `JSAnalyzer`).
    - Реалізує компіляцію AST у проміжне представлення Raw DRAKON IR.
    - Проводить лінгвістичний пошук правил проектування схем за допомогою BM25 ретривера (`rank-bm25`) та виконує семантичну валідацію отриманих схем (`ir_validator.py`).

## 4. Пропозиція уніфікації

Для переходу на єдиний, підтримуваний та гнучкий фреймворк пропонується наступна стратегія:

### А. Спільний LLM-клієнт (`services/shared/drakon_shared/llm_client.py`)
Створити єдиний модуль для взаємодії з LLM, який підтримуватиме:
- Автоматичний вибір провайдера та моделі на основі системних змінних середовища.
- Вбудовану логіку повторних запитів (retries) та обробку помилок обмеження частоти запитів (Rate Limits).
- Підтримку як OpenAI-сумісного (`chat/completions`), так і Anthropic/AGY-сумісного (`/v1/messages`) форматів.

### Б. Спільна структура Knowledge Base та Memory
- Перенести `memory_manager.py` у спільний пакет `services/shared/drakon_shared/memory.py`, усунувши необхідність брудного хаку із `sys.path.append` у кожному сервісі.
- Запровадити єдиний формат для баз знань. Дозволити `docs-agent` та `architect-agent` також використовувати локальний BM25 ретривер для швидкого пошуку по документації та архітектурних концептах.

### В. Інтеграція `ai-memory` як спільної пам'яті
`ai-memory` (що працює на `192.168.3.184:49374`) — це надзвичайно потужний інструмент для крос-агентної синхронізації та відстеження життєвого циклу сесій (hooks).
- **Чи варто інтегрувати?** **ТАК, АЛЕ** для чітко визначених задач:
  - **Для життєвого циклу та handoff**: `ai-memory` ідеально підходить для фіксації початку та завершення сесій агентами (через `POST /hook?event=SessionStart\|Stop`), створюючи спільний часовий графік (timeline) розробки.
  - **Не для дрібного CRUD-запису**: Спроба використати його як стандартну базу даних через API типу `POST /wiki/pages` не рекомендується і повертає `404 Not Found`. Сервер `ai-memory` розрахований на взаємодію через MCP-інструменти або автоматичне захоплення контексту з гачків (hooks).
  - **Висновки**: Локальна пам'ять `mempalace` (ChromaDB + diary) залишається основним сховищем глибоких семантичних знань та особистих щоденників агентів (оскільки вона локальна, швидка та підтримує семантичний векторний пошук). `ai-memory` має виступати як **глобальний шар координації та handoff** (хто що зробив, які результати поточної сесії).

## 5. Наступні кроки

1. **Task A1 (Refactoring shared packaging)**:
   Перенести `memory_manager.py` у пакет `drakon_shared` та оновити імпорти в усіх трьох агентах.
2. **Task A2 (Unified LLM Client)**:
   Створити `drakon_shared/llm_client.py` і перевести `refiner.py`, `docs_chat.py` та `architect_chat.py` на його використання.
3. **Task A3 (Drakon Agent memory activation)**:
   Активувати використання `MEMORY.md` для `drakon-agent` (через новий `drakon_shared` менеджер пам'яті), щоб він міг пам'ятати специфічні правила проекту, які користувач повідомляє в чаті.
4. **Task A4 (ai-memory MCP integration)**:
   Налаштувати підключення MCP-клієнта `ai-memory` до всіх трьох агентів, щоб вони могли шукати по спільному timeline-вікі під час виконання завдань.
