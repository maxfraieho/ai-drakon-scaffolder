## 3. Executive summary

The system today has **no real trust boundary** between browser and server on the deterministic execution path. Concretely:

- The browser **mints its own security policy** (`createDefaultSpec`, one call site: `src/hooks/usePipelineExecution.ts:69`) and sends it to the Worker as `harness_spec`. The Worker forwards this **byte-for-byte, unvalidated**, to the Appwrite Function running the deterministic engine. The engine treats the client-supplied `gates` config as authoritative. `validateHarnessSpec` exists (`src/lib/harness/harness-spec.ts:14`) but has **zero callers anywhere in the repository**.
- Every authenticated caller — whoever they are, whatever token they present (a shared `MCP_API_KEY`, a Worker-issued JWT, or a real Appwrite JWT) — is collapsed by `verifyOwnerAuth` (`cloudflare-worker/worker-mcp-drakon.js:438-462`) into a single `{ role: 'owner' }` principal. There is no tenant concept anywhere on the request path. A `sub` field exists on the returned principal but is **never forwarded** past the Worker to the engine.
- The execute route itself (`POST /v1/pipeline/execute-deterministic`) requires `verifyOwnerAuth` server-side, but the frontend client (`pipeline-client.ts:35-38`) **sends no `Authorization` header at all** — a live contract mismatch, not just a design gap. The paired status-polling route (`GET /v1/pipeline/execute-deterministic/status`) has **no authentication whatsoever** and leaks any execution's full output/logs to anyone who can guess or observe an `execution_id`.
- Roughly two dozen additional Worker routes (full list in §7) are unauthenticated or rely on a shadowed/broken auth check, spanning knowledge-base search, codegen, compilation, semantic-graph generation, GitHub repo reads, and WebSocket sync — all using the Worker's server-side Admin key on the caller's behalf with zero caller verification.
- **D1 is declared with a strict, well-designed tenant schema (`infrastructure/d1/schema.sql`, every table has `tenant_id`, correct indexes/uniqueness constraints) but is bound in exactly zero `wrangler.toml` files anywhere in the repository.** Every D1 table today is schema-only — 0 read call sites, 0 write call sites, at runtime. The `pipeline_runs` table that should record executions has never been written to. Appwrite's `audit_log` collection is similarly declared but never written.
- Consequently: gate verdicts are computed correctly (the four-gate logic itself, in `packages/policy-engine`, is clean and well-isolated — this is good news for Phase 3) but are **never persisted anywhere**. They live only in the Appwrite Function's ephemeral response (which the current Appwrite Education plan actually drops — recovered only via a base64-encoded regex extraction from execution *logs*, worker-mcp-drakon.js:4755-4766) and in transient React state on the client. Nothing is replayable. Nothing is auditable.
- The frontend has **two entirely separate execution paths** (deterministic vs. a legacy graph-pipeline/SSE path routed to `architect-agent`), and only one of them carries any harness-spec/policy concept at all — the legacy path has no gates, no spec, no verdicts, a completely different event shape, and talks to a different backend service entirely.

None of this is a surprise given Phase 3's stated target principles — this inventory exists to make the starting point precise and evidence-backed rather than assumed. The good news: the gate-evaluation seam (`packages/policy-engine`) is already clean and requires no changes. The actual missing pieces are exactly two: **who resolves/owns the harness spec server-side**, and **where persisted state (specs, tenants, runs, events, audit) actually lives** — because right now, the answer to both is "nowhere."

## 10. Policy/engine trust-boundary analysis (Section E)

*Investigated by Oracle Claude.*

1. **Gate ownership:** all four gate *logics* live in `packages/policy-engine/src/index.ts` (`evaluateSafetyGate:48`, `evaluatePolicyGate:72`, `evaluateConfidenceGate:135`, `evaluateCostGate:198`). Orchestration (gate order, token/branch simulation, NotebookLM mock) stays in `deterministic-engine/main.ts:165-242`.
2. **Spec supplier:** the client (`createDefaultSpec`), forwarded verbatim through the Worker.
3. **Trust:** untrusted/client-forwarded. Worker does a raw `JSON.stringify` passthrough (`:4712`); engine only checks `harness_spec.gates` is present (`:95`); `validateHarnessSpec` is never called anywhere on this path.
4. **`capabilityMatches`:** single shared definition (`policy-engine/src/index.ts:34`), no duplication found repo-wide.
5. **Result type stability:** stable — `GateVerdict` in `harness-contract/src/index.ts:57-63`, `{gate, allowed, score?, reason?, metadata?}`.
6. **Identity in decisions:** none — `GateVerdict` carries no tenant/spec/run/node/capability id (`node_id` lives on the enclosing `PipelineEvent`, not the verdict itself; a computed `requestedCap` is discarded before it reaches the verdict).
7. **Persisted:** no, nowhere.
8. **Seam cleanliness:** the gate-evaluation seam is clean — swapping to a server-resolved spec changes only *who fills the request payload* (Worker resolves+injects vs. today's pure forwarding), not gate semantics. The entanglement risk is elsewhere: no server tier currently *owns* spec resolution at all, and the engine inlines nondeterministic simulation logic (`Math.random` token/branch sim, NotebookLM mock) that Phase 3 must be careful not to disturb while building the resolution seam around it.
9. **Characterizing tests found:** `services/deterministic-engine/src/__tests__/main.characterization.test.ts`, `packages/policy-engine/src/__tests__/policy-engine.test.ts`.
10. **Invariants that must not change** (extracted from the above tests plus the policy-engine header comment):
    - Gate order always `safety → policy → confidence → cost`.
    - A skipped gate (`shouldEvaluate` false) returns `allowed:true` with no `reason`/`score`/`metadata`.
    - `require_human_approval` is declared in the spec type but **never enforced** — no pause, no block, anywhere. (This is a pre-existing gap, not something Phase 3 Slice 0 should treat as a bug to fix silently.)
    - Confidence gate is deterministic: starts at `0.65`, `+0.15` per retry.
    - Tool nodes cost a fixed 200 tokens; LLM nodes use `Math.random()` in the 1000-5000 range, and this randomness stays in the engine, not the policy package.
    - A safety block halts immediately with events `[node_start, gate_blocked, error]`, and the overall `success` flag is still `true` (i.e. "gate blocked" is not itself treated as an execution failure).
    - A breakpoint halts before the node runs, `success:true`.

## 16. Recommended Phase 3 implementation slicing

**Important correction to the originally proposed sequence, based on evidence from §8 (R5):** Slice 3.1 as titled ("server-side harness spec persistence/read path") is not actually implementable first — there is no bound D1 database to persist *into*. The D1 binding step must be pulled to the front of whichever slice first needs to write anything, or made an explicit Slice 3.0.5.

### Slice 3.1 — D1 binding + server-side harness spec persistence/read path
- **Files:** all `wrangler.toml`/`wrangler-antigravity.jsonc` files needing a `[[d1_databases]]` binding (likely just `cloudflare-worker/wrangler.toml` and `cloudflare-worker/worker-wrangler.toml`, whichever is actually deployed — needs confirmation, see §18); new `infrastructure/d1/migrations/00XX_harness_specs.sql`; a new `harnessSpecRepository`-style module in the Worker.
- **Dependencies:** none — this is the true first step.
- **Tests required:** repository unit tests (CRUD against a local/miniflare D1 instance); no production route wired yet.
- **Rollback boundary:** clean — an unused table + binding, nothing reads from it yet.
- **External API change:** none.
- **Compatibility window:** not needed yet.

### Slice 3.2 — Ingress validation and forged-spec rejection
- **Files:** `cloudflare-worker/worker-mcp-drakon.js` (`handleDrakonExecuteDeterministic`), `src/lib/harness/harness-spec.ts` (`validateHarnessSpec` gets its first real caller), the characterization test recommended in §14.
- **Dependencies:** Slice 3.1 (need somewhere to resolve `specId` from).
- **Tests required:** the new "status route currently has zero auth" characterization test (frozen *before* changing), plus a new test asserting a request body containing `harnessspec` is rejected with 400 once the flag is flipped.
- **Rollback boundary:** needs a feature flag or staged rollout — this changes a live external contract (R3, R13). Recommend a compatibility window: accept `specId` if present, still accept legacy `harness_spec` with a deprecation warning, only hard-reject after client migration confirmed.
- **External API change:** **yes** — this is the riskiest slice from a compatibility standpoint.

### Slice 3.3 — Tenant resolution and scoped repositories
- **Files:** `verifyOwnerAuth` → `resolveTenant` in `worker-mcp-drakon.js`; every repository/query touching D1 or Appwrite gets a `tenantId` parameter threaded through; fixes the unauthenticated status route (R2) as part of the same pass since both need the same tenant-check primitive.
- **Dependencies:** Slice 3.1 (tables to scope), ideally after 3.2 (spec resolution already server-side).
- **Tests required:** integration tests for every call site in §6's table — 10 call sites, all currently untested at the Worker level.
- **Rollback boundary:** larger — touches many call sites at once. Consider sub-slicing by route category if the diff grows unwieldy.
- **External API change:** yes for any currently-fully-open route that becomes auth-required (R4's list is explicitly out of this slice's scope per the coordinator's non-goals, but the *status* route specifically is in scope since it's the deterministic-execution status route named in R2).

### Slice 3.4 — Deterministic engine migration to resolved specs
- **Files:** `services/deterministic-engine/src/main.ts` (stop destructuring `harness_spec` from the client payload, read from the resolved spec passed down from the Worker instead).
- **Dependencies:** 3.1, 3.2, 3.3.
- **Tests required:** re-run `main.characterization.test.ts` unmodified as a regression gate (§10.10's invariants must hold); add a new test proving a client-supplied `harness_spec` field is now ignored, not trusted.
- **Rollback boundary:** clean, single-service change once its dependencies exist.
- **External API change:** none beyond what 3.2 already introduced.

### Slice 3.5 — HarnessAdapter integration
- Insufficient evidence gathered this slice to size this precisely — the coordinator's own principle list doesn't fully specify what "HarnessAdapter" is meant to abstract over (single adapter for the deterministic engine only, or a seam meant to also eventually cover the legacy graph-pipeline path?). **Flagging as an open question for the architect (§18) rather than guessing a file list.**

### Slice 3.6 — Run-event and audit persistence
- **Files:** new `infrastructure/d1/migrations/00XX_run_events.sql` (schema per R11 — include `seq`), new Appwrite `audit_log` writer wired into the Worker's response-handling path, `pipeline_runs` table gets its first writer.

- **Rollback boundary:** additive — nothing existing reads from these tables yet, low risk to add.
- **External API change:** none required, though it's the natural point to also expose a new read endpoint for trace/audit UI work (out of this slice's scope).
