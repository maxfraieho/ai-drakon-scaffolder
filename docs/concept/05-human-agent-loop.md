# 05 — Human-Agent Loop: модель взаємодії людини та агента

## Концепція

AI-DRAKON реалізує **не автономну AI-систему**, а модель **розподіленого мислення**. Агенти виконують детерміністичну або LLM-роботу, людина залишається архітектором рішень і ревьюером артефактів. Ця модель свідомо відкидає "натисни і чекай" на користь **активного партнерства**.

```
Людина (архітектор)
    │
    ├── Ставить задачу
    ├── Оцінює IR-діаграму
    ├── Редагує структуру в UI
    └── Ухвалює або відхиляє результат
    
AI-агент (виконавець)
    │
    ├── Вимірює складність коду
    ├── Транслює логіку у DRAKON IR
    ├── Валідує IR проти топологічних правил
    └── Генерує код з IR
```

---

## Чотири ролі людини в системі

### 1. Ініціатор (Input Provider)
Людина подає вхідні дані: Python-код для аналізу або DRAKON IR для генерації коду. Якість вхідних даних безпосередньо впливає на якість результату.

**Практичне правило:** Код, який читабельний людиною, дає кращий IR. Якщо функція перевантажена відповідальностями — IR відобразить цей хаос.

### 2. Архітектор схеми (IR Curator)
Отримавши IR від Pipeline A, людина може:
- **Прийняти** — імпортувати в редактор і використати
- **Відхилити** — запустити "Новий аналіз" з покращеним кодом
- **Відредагувати** — змінити вузли/зв'язки у графічному редакторі вручну

Редактор DiagramsPage дозволяє редагувати IR безпосередньо. Це ключова точка контролю: людина коригує те, що агент згенерував невірно (особливо для `deep`-рівня складності).

### 3. Специфікатор поведінки (Behavior Specifier)
При запуску Pipeline B (IR → код) людина може задати:
- Цільову мову (`python`, `typescript`, `javascript`)
- Опис поведінки (необов'язковий текстовий контекст)

Опис допомагає агенту коректно обробляти неоднозначності IR — наприклад, якщо назви вузлів псевдокодові.

### 4. Ревьюер результату (Code Reviewer)
Отриманий з Pipeline B код — **пропозиція, не фінальний результат**. Людина оцінює:
- Чи збігається поведінка з очікуваною
- Чи немає зайвого або відсутнього коду
- Якість іменування та стиль

## Цикл взаємодії (повний сценарій)

```
1. Розробник має функцію, яку треба задокументувати/зрозуміти
    ↓
2. [Pipeline A] Вставляє код у CodeAnalysisPanel → "Аналізувати"
    ↓
3. Агент: вимірює CC, обирає шлях, генерує IR з валідацією
    ↓
4. Розробник бачить список функцій з CC-скорами
    ↓
5. Для функцій, що цікавлять → "Імпортувати діаграму"
    ↓
6. DiagramsPage відкриває IR в редакторі
    ↓
7. Розробник вивчає схему, редагує за потреби
    ↓
8. [Pipeline B] "Генерувати код" → обирає мову → "Генерувати"
    ↓
9. Агент: генерує код з IR, перевіряє синтаксис у циклі
    ↓
10. Розробник отримує код → "Копіювати" → вставляє в проект
```

## Де агент авторитетний, де — людина

| Рішення | Хто приймає | Чому |
|---------|-------------|------|
| Цикломатична складність | Агент (radon) | Математично однозначно |
| Тип діаграми (Primitive/Silhouette) | Агент (правило CC) | Детерміністичне правило |
| Маппінг AST → IR (CC ≤ 10) | Агент (PythonAnalyzer) | Без варіативності |
| Маппінг складної логіки → IR | LLM + людина-ревьюер | LLM може помилятись |
| Яку функцію імпортувати | Людина | Контекст задачі |
| Цільова мова генерації | Людина | Вимоги проекту |
| Якість згенерованого коду | Людина | Стиль, архітектура |

## Принцип мінімального втручання агента

Ralph Loop (Pipeline A) і Syntax Loop (Pipeline B) обмежені **3 ітераціями**. Це свідомо:

- Якщо за 3 спроби IR не валідний — код занадто складний для автоматичної трансляції. Потрібна ручна декомпозиція.
- Якщо за 3 спроби синтаксис не коректний — IR містить неоднозначності. Потрібний уточнений опис.

Агент сигналізує людині через `validation_errors` і `syntax_errors` — не замовчує проблеми.

## Feedback Loop: як система вчиться

Поточна версія системи не має автоматичного feedback loop (збір виправлень → покращення моделі). Це запланована функціональність (Phase 3):

```
Людина редагує IR  →  дельта зберігається  →  KB оновлюється
Людина відхиляє код →  коментар зберігається →  prompt покращується
```

До реалізації цього циклу — **база знань оновлюється вручну** через редактор Notes у docs-agent.

---

## Multi-agent оркестрація

Три агенти можуть взаємодіяти в ланцюжку:

```
docs-agent (аналізує кодову базу)
    │ структурований опис
    ▼
architect-agent (будує IR для ключових функцій)
    │ DRAKON IR
    ▼
drakon-agent (валідує, рендерить)
    │ validated IR
    ▼
Редактор (людина)
```

Поточна реалізація: агенти незалежні, взаємодія через frontend. Пряма міжагентна комунікація — Phase 3.
